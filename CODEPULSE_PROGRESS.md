### Phase 2.2 — Embedded (sqlite-vec-backed) ANN vector index

- **Scope determined from the roadmap's own text** (§36 Phase 2's objective, unchanged from Phase 2.1: *"replace brute-force search internals without changing the ranking contract"*; §37 item 2.2: *"Embedded ANN vector index adapter behind existing VectorIndex call sites"*; §45 backlog B13: *"Embedded ANN vector index... `search/vector.py` replacement... Dependency: B4... DoD: Same as above for semantic search"* [B12's benchmark half is Phase 2.5's job, not this milestone's — no latency numbers are reported here]; §7 Storage Decision: *"a local vector index (e.g., `sqlite-vec` or a persisted HNSW structure via `hnswlib`, avoiding pgvector's Postgres dependency entirely for local mode)"*).
- **Dependency selection was forced by the real development environment, not silently chosen.** §7 names two candidate libraries without picking between them. `hnswlib` was attempted first (`pip install hnswlib`) and **failed**: PyPI carries only a source distribution for this platform/Python combination (no prebuilt wheel for CPython 3.11 / win_amd64), and building it requires a C++ compiler (`Microsoft Visual C++ 14.0 or greater`) that is not installed on this machine — confirmed by a direct, failed install attempt, not assumed. Installing system-level build tooling was judged out of scope for this milestone. `sqlite-vec` (0.1.9) was tried next and **installed cleanly** (a prebuilt `win_amd64` wheel exists) — used instead. This is disclosed here and in `codepulse/search/vector.py`'s own module docstring, not silently substituted.
- **A real, material nuance about the library actually used, verified experimentally rather than assumed**: `sqlite-vec` 0.1.9's `vec0` virtual table performs an **exact** (brute-force) distance computation over every stored vector at this version — it is not yet an approximate/graph-based nearest-neighbor structure the way `hnswlib`'s HNSW algorithm is. Confirmed by direct testing: every query tried against the new adapter produced results *identical* to the pre-Phase-2.2 NumPy implementation, not merely similar. This still satisfies §7's literal wording (`sqlite-vec` is one of its two explicitly named options) and is a genuine embedded, compiled-native vector index rather than a pure-Python/NumPy one — but "ANN" in §36/§37's own wording is, at this specific library version, not literally approximate. A beneficial side effect: retrieval remains fully deterministic (CLAUDE.md §4's permanent invariant) as a direct, simple consequence, which an approximate structure would not guarantee as straightforwardly.
- **The real, installed Python binding (`sqlite_vec` 0.1.9) was directly introspected and round-trip-tested before any adapter code was written** — `sqlite_vec.load(conn)` (loads the extension into a `sqlite3.Connection`), `sqlite_vec.serialize_float32(vector)` (packs a vector into the wire format `vec0` expects), a `CREATE VIRTUAL TABLE ... USING vec0(embedding float[N] distance_metric=cosine)` schema, `INSERT INTO ...(rowid, embedding) VALUES (?, ?)` (explicit integer rowids, confirmed reusable after a delete, confirmed safe to leave unused since this milestone never deletes), and the KNN query form `SELECT rowid, distance FROM ... WHERE embedding MATCH ? AND k = ? ORDER BY distance` (confirmed: `distance` is `1 - cosine_similarity`; `k` larger than the corpus size safely caps rather than erroring; `k = 0` and an empty table both return `[]` without error; an all-zero, un-normalizable query vector returns `distance = NULL`, not an error or NaN — handled explicitly as similarity 0.0, a degenerate case CLAUDE.md's no-pseudo-embedding invariant means the real embedder never actually produces).
- **A genuine, necessary design adjustment discovered and verified experimentally**: the underlying `sqlite3.Connection` is constructed with `check_same_thread=False`. FastAPI/Starlette's plain-`def` route handlers (every endpoint in this app, including the Phase 1.3 background-task indexing path) run on a shared threadpool, so the same `IndexingEngine`/`VectorIndex` instance can legitimately be called from more than one OS thread across its lifetime — confirmed this is a real characteristic of the existing app, not a new one introduced this milestone. Python's `sqlite3` module refuses cross-thread use of one connection by default (verified: raises `ProgrammingError` without this flag); the pre-Phase-2.2 pure NumPy/list implementation had no such restriction. `check_same_thread=False` was verified experimentally (a real cross-thread write-then-read round trip) to work correctly for this codebase's actual usage pattern. This is disclosed as a necessary adjustment to avoid Phase 2.2 introducing a *new* hard-crash mode, not a claim of full concurrent-write safety — this codebase has no locking around `bm25_index`/`vector_index` today either (unchanged, pre-existing, out of this milestone's scope, matching Phase 2.1's own precedent for `BM25Index`).
- **Architectural decisions made** (all resolved and implemented, none silently inferred):
  1. **Source of truth: SQL remains authoritative; the vector index is a derived, rebuildable search artifact** — unchanged from before Phase 2.2. `hydrate_repository()`/`hydrate_all()` (Phase 0.5, untouched by this milestone) continue to populate the index from durable `EmbeddingModel` rows exactly as before; the sqlite-vec-backed structure itself is an **in-memory-only** (`sqlite3.connect(":memory:", ...)`) SQLite database, confirmed experimentally to hold no on-disk state.
  2. **`.vectors` remains a genuine, correctly-shaped `numpy.ndarray`** (`tests/test_embedding_persistence.py` asserts `.vectors.shape`/`.vectors.shape[1]` directly) — maintained as a parallel, redundant copy of every normalized vector ever added, alongside the sqlite-vec table that actually answers `search()` queries. This is pure bookkeeping for contract compatibility, not a performance-relevant structure, disclosed as such.
  3. **Repository isolation is unchanged**: `VectorIndex` itself has zero awareness of repositories (as before) — the existing `_repo_filter` post-filtering logic in `IndexingEngine.search()` (Phase 0.6, untouched) continues to enforce scoping by reading `metadata["repo_id"]` off each returned candidate, exactly as it always has. `tests/test_repository_scoped_search.py`'s full semantic/hybrid isolation suite (11 tests, including the adversarial overlapping-symbol scenario) passes unmodified.
  4. **No repository-replacement (delete-by-`repo_id`-then-add) idempotency was implemented** — a deliberate scope decision, not an oversight. Unlike Phase 2.1's `BM25Index.remove_repo`, `VectorIndex.add`/`add_batch` remain pure-append operations, exactly matching the pre-Phase-2.2 implementation's own existing behavior. **This is a real, pre-existing gap** (re-indexing an already-indexed repository was already silently accumulating duplicate vector entries before this milestone, since the old `VectorIndex` had no such logic either) that Phase 2.1's analogous fix for `BM25Index` did not extend to here. CLAUDE.md §12 ("do not make opportunistic cleanup... unless required by the current milestone or the roadmap explicitly requires it") governs this: §37 item 2.2's literal text is "adapter... behind existing `VectorIndex` call sites," not an idempotency fix, so this was disclosed rather than silently expanded into. **Explicitly flagged to the user in this session's own final report** as a candidate fast-follow-up, not applied unilaterally. A new test (`test_known_limitation_repeated_add_of_the_same_doc_id_accumulates_duplicates`) documents this exact, current characteristic explicitly, so it cannot silently change (in either direction) without a test noticing.
  5. **Score derivation is unchanged in formula**: `similarity` is recovered as `1 - distance` from sqlite-vec's own cosine distance output, then `relevance_score = clamp((similarity + 1) / 2, 0, 1)` and `embedding_distance = clamp(1 - similarity, 0, 2)` — the exact same formulas the pre-Phase-2.2 NumPy implementation used, only the source of the raw `similarity` number changed (from `np.dot` to a SQL KNN query). `HybridRanker` was **not modified**.
  6. **Vector normalization is unchanged**: both indexed and query vectors are still L2-normalized in Python (via NumPy) before being handed to sqlite-vec, exactly as the pre-Phase-2.2 implementation normalized them before `np.dot` — sqlite-vec's own `distance_metric=cosine` is used as a defense-in-depth match to this, not a replacement for it.
- **Files changed**: `codepulse/search/vector.py` (full rewrite of `VectorIndex`'s internals, same class name/module path/public interface), `pyproject.toml` (new dependency `sqlite-vec>=0.1.9,<0.2.0`, justified by §7's explicit naming), `tests/test_sqlite_vec_semantic_index.py` (new file, 16 tests: 14 unit tests directly against `VectorIndex` — empty index, single/multiple documents, the exact pre-Phase-2.2 `test_vector_index_search` fixture reproduced as a ranking regression proof, similarity/relevance/distance ranges and formulas, metadata and doc_id round-trip, determinism, `top_k` truncation, `.vectors`/`.doc_ids`/`.dimension` attribute contracts, unnormalized-vector handling, all-zero-query safety, empty-batch safety — plus 1 test explicitly documenting the known repeated-add-accumulates-duplicates limitation above, and 1 test proving a genuine vector-layer failure propagates through the existing Phase 1.6 structured 500 envelope rather than a hand-rolled shape). **No line in `codepulse/indexer/engine.py` changed** — unlike Phase 2.1 (which needed one new `remove_repo` call site), Phase 2.2's literal scope required zero call-site changes, since no repository-replacement behavior was added.
- **No production code outside the above was touched**: `codepulse/search/bm25.py`, `codepulse/search/ranker.py`, `codepulse/indexer/engine.py`, `codepulse/api/app.py`, `codepulse/config.py`, `codepulse/storage/db.py`, and every Phase 1/2.1 module are all untouched — confirmed via `git diff --stat` showing exactly the two modified files plus one new test file listed above.

### Phase 2.1 — Tantivy-backed embedded lexical index

- **Scope determined from the roadmap's own text** (§36 Phase 2's objective: *"replace brute-force search internals without changing the ranking contract"*; §37 item 2.1: *"Tantivy-backed lexical index adapter behind existing BM25Index call sites"*; §45 backlog B12: *"Tantivy-backed lexical index... `search/bm25.py` replacement... Dependency: B4... DoD: Benchmarked latency at 10K/100K-file tiers documented"*). This milestone implements the adapter itself; B12's *benchmark* half of its own DoD is explicitly Phase 2.5's job (§37 item 2.5), not claimed here — no latency/performance numbers are reported anywhere in this update, since none were measured.
- **A dedicated read-only architecture gate ran first** (this session, before any code was written), producing a full design report (16 sections: current-interface documentation, ranking-contract analysis, Tantivy lifecycle design, source-of-truth decision, storage location, repository isolation strategy, document schema, score compatibility, idempotency, restart survivability, failure behavior, dependency verification plan, test plan, out-of-scope list) with a **READY FOR PHASE 2.1 IMPLEMENTATION** verdict. Implementation below follows that report, with corrections noted where direct repository evidence (the actually-installed Tantivy binding, and a fuller re-read of the existing test suite) required adjusting a design detail the gate had flagged as unverified.
- **Tantivy version actually used: `tantivy` 0.22.2** (the exact pip-installable release; `tantivy.__version__` reports itself as `"tantivy v0.22.0, index_format v6"` — the package version and the internal version string differ slightly, both satisfy the already-declared `pyproject.toml` constraint `tantivy>=0.22.0,<0.23.0`, which was **not changed**). **Installed via `pip install "tantivy>=0.22.0,<0.23.0"` directly, not via `pip install -e .`** — the project's own editable install is currently broken by a pre-existing, unrelated packaging configuration issue (`pyproject.toml` declares no explicit package list, and setuptools' automatic flat-layout discovery finds two top-level packages, `alembic` and `codepulse`, and refuses to guess; confirmed via a direct `pip install -e .` attempt before installing tantivy any other way). This is **not a Phase 2.1 defect and was not fixed** (CLAUDE.md §12: no opportunistic fixing of unrelated technical debt) — recorded here as a genuine, pre-existing gap for whoever next needs a clean editable install of this project.
- **The real, installed Python binding was directly introspected before any adapter code was written** (`dir()`/`help()` against the actual imported `tantivy` module, plus small isolated round-trip experiments — not assumed from upstream Rust Tantivy documentation or general training knowledge). Verified APIs actually used: `tantivy.SchemaBuilder.add_text_field(name, stored=, tokenizer_name=)` / `.add_integer_field(name, stored=, indexed=, fast=)` / `.add_json_field(name, stored=)` / `.build()`; `tantivy.Index(schema)` (no path argument constructs a genuine in-RAM index — confirmed experimentally, no `Index.create_in_ram` classmethod exists in this binding, contrary to what the architecture gate had assumed by name); `Index.writer(heap_size=, num_threads=)` returning an `IndexWriter` that is **safe to create once and reuse across many add/delete/commit cycles** (confirmed experimentally — not a one-shot object, contrary to nothing in the gate but worth confirming rather than assuming); `IndexWriter.add_document(Document)`, `.delete_documents(field_name, field_value)` (exact-term deletion — confirmed it silently no-ops when nothing matches, needed for the empty-repository and first-index cases), `.commit()`; `Index.reload()` + a **freshly-fetched** `Index.searcher()` after every commit (confirmed experimentally that an already-held `Searcher` instance is a frozen snapshot and does **not** see documents added after it was fetched — a `Searcher` must be re-fetched post-commit, not reused indefinitely); `tantivy.Document.add_text/add_integer/add_json` + `.get_first(field)` (confirmed a Python dict passed to `add_json` round-trips as a real `dict`, not a JSON string, and a field never set on a given document reads back as `None`, not an error — needed for the `repo_id=None` direct-`BM25Index`-usage case); `tantivy.Query.term_query(schema, field, value)` + `tantivy.Query.boolean_query([(Occur.Should, query), ...])` for an OR-combined multi-token query (built manually from this project's own existing `tokenize_code()` output, deliberately **not** using `Index.parse_query()` against a raw user query string — avoids both Tantivy's own query-language special-character parsing entirely and any need to pick/register a custom tokenizer that approximates `tokenize_code`'s snake_case/camelCase splitting, since indexing and querying both go through the *exact same*, already-tested `tokenize_code` function before Tantivy ever sees the text); `Searcher.search(query, limit=N)` returning `SearchResult.hits` as `(score: float, DocAddress)` pairs, already sorted descending; `Searcher.doc(doc_address)` for stored-field retrieval; `Searcher.num_docs`.
- **Architectural decisions made** (all previously flagged by the architecture gate as requiring an explicit choice, now resolved and implemented — none silently inferred):
  1. **Source of truth: SQL remains authoritative; the Tantivy index is a derived, rebuildable search artifact.** No cross-store transactional coordination, no index persistence/versioning/corruption-recovery infrastructure was introduced — matches the pre-existing `BM25Index`'s own characteristic exactly, just re-implemented on Tantivy's engine internally.
  2. **In-memory Tantivy only.** `tantivy.Index(schema)` is constructed with no path argument (confirmed experimentally: genuinely in-RAM, nothing written to disk). No `.codepulse/` directory, no cache-directory configuration, and no on-disk persistence were introduced in this milestone.
  3. **One shared Tantivy `Index` per `IndexingEngine` instance** (mirrors the pre-Phase-2.1 `BM25Index`'s own one-per-engine shape exactly) — **not** a physically separate index per repository. Every lexical document carries `repo_id` (as a genuinely indexed+fast schema field, not merely a stored, unindexed one), and the existing `_repo_filter` post-filtering logic in `IndexingEngine.search()` (Phase 0.6, unchanged by this milestone) continues to enforce repository isolation exactly as it already did — `BM25Index.search()`'s returned `metadata["repo_id"]` is the same field that logic has always read. Physical per-repository index segmentation (mentioned only in the roadmap's risk register, §42, as an optional defense-in-depth mitigation, never as a Phase 2 task-list/backlog requirement) was **not** adopted — out of scope for this milestone, consistent with the architecture gate's own analysis.
  4. **Repository-replacement idempotency: delete-by-`repo_id`-then-add-then-commit.** `IndexingEngine.index_directory()` now calls a new `BM25Index.remove_repo(repo_id)` method once, immediately before the existing per-symbol `add_symbol` loop, deleting every lexical document previously indexed for that repository via `IndexWriter.delete_documents("repo_id", repo_id)` (an exact-term deletion, confirmed safe/no-op when the repository has no existing documents — covering both the first-ever index of a repository and an empty repository). This closes a **real, pre-existing, previously-untested gap**: the old parallel-list `BM25Index` had no doc_id-based replace logic at all, so repeated `index_directory()` calls on an already-indexed repository silently accumulated duplicate lexical documents forever (discovered by direct code inspection during the architecture gate, and confirmed live by the fact that `tests/test_restart_idempotency.py`'s own `test_repeated_reindex_is_idempotent_and_identifiers_stay_stable` — which re-indexes the same repository 5 times into one engine — asserted SQL row-count stability but never checked `bm25_index.num_docs`, so the accumulation had never been caught). Fixing this was judged in-scope because Tantivy's `delete_documents` makes it essentially free and it has zero ranking-contract impact — not because the roadmap's literal Phase 2.1 text mandates fixing pre-existing gaps.
  5. **Tokenization: reuses the existing, already-tested `codepulse.search.tokenizer.tokenize_code`** for both indexing and querying, feeding the resulting space-joined token list into a Tantivy text field configured with the built-in `"whitespace"` tokenizer (not Tantivy's own `"default"` tokenizer, which does not split camelCase identifiers the way `tokenize_code` does). The search corpus construction itself (`name*3 + signature + docstring + extra_text + body[:1000]`) is byte-for-byte unchanged from the pre-Tantivy implementation — no field-specific boosting, no split name/signature/docstring fields, no relevance redesign.
  6. **Score normalization is unchanged in formula**: `normalized_score = raw_score / max(raw_score across this query's result set)`, with the same zero-max safety fallback (`max_score = 1.0` if the true max is `<= 0`) the pre-Tantivy implementation used — reproduced exactly, not reinvented. Tantivy's own BM25 scorer produces genuinely different raw numeric values than the old hand-rolled Okapi BM25 formula (expected and explicitly permitted — the roadmap's "ranking contract" is the *shape/meaning* `HybridRanker` consumes, not bit-identical arithmetic); `normalized_score` remains a float in `[0, 1]`, `HybridRanker` was **not modified**.
  7. **`.k1`/`.b` remain real, settable, readable attributes** (`BM25Index(k1=..., b=...)`, `tests/test_config.py` reads them directly) even though Tantivy's own Python binding exposes no configurable BM25 k1/b parameter anywhere in `Query`/`Searcher`/`Index` (confirmed by full `dir()` introspection — no such method exists). Tantivy's fixed internal BM25 implementation is used as-is; `.k1`/`.b` are preserved purely for interface compatibility, disclosed here rather than silently glossed over.
- **`IndexingEngine.symbols_by_id`/`.symbol_repo_map` staleness is unchanged, not fixed, and not newly introduced by this milestone**: these two dicts (used by the hybrid-search graph-score computation, unrelated to `BM25Index`) already only ever *set* entries for symbols found in the current run, never removing an entry whose symbol no longer exists after a re-index. This pre-existing characteristic is harmless in practice (a stale key never appears in the fresh, repo-replaced Tantivy candidate lists, so it's simply never touched by `fuse()`), was already true before Phase 2.1, and fixing it is out of scope for this milestone (unrelated data structure, not a `BM25Index` call site).
- **Files changed**: `codepulse/search/bm25.py` (full rewrite of `BM25Index`'s internals, same class name/module path/public interface), `codepulse/indexer/engine.py` (one new line, `self.bm25_index.remove_repo(repo_id)`, plus an explanatory comment, immediately before the existing per-symbol lexical-population loop — no other line in this file changed), `pyproject.toml` (one comment updated to note `tantivy` is now actually wired in, no version/dependency-list change), `tests/test_restart_idempotency.py` (one new assertion added to the existing 5-iteration re-index test, proving the previously-undetected lexical-duplication gap above is now closed — no existing assertion removed or weakened), `tests/test_tantivy_lexical_index.py` (new file, 21 tests: 15 unit tests directly against `BM25Index` — empty index, single/multiple documents, the exact pre-Tantivy `test_bm25_search` fixture reproduced as a ranking regression proof, raw/normalized score types and range, metadata and doc_id round-trip, determinism, `top_k` truncation, no-non-matching-results, `.doc_ids`/`.num_docs`/`.k1`/`.b` attribute contracts, `remove_repo` no-op safety — plus 6 integration tests through the real `IndexingEngine` covering exactly Cases A-F of the required repository-replacement behavior, and 1 test proving a genuine lexical-layer failure propagates through the existing Phase 1.6 structured 500 envelope rather than a hand-rolled shape).
- **No production code outside the above was touched**: `codepulse/search/vector.py`, `codepulse/search/ranker.py`, `codepulse/api/app.py`, `codepulse/config.py`, `codepulse/storage/db.py`, and every Phase 1 module (`auth.py`, `security.py`, `jobs.py`, `rate_limit.py`, `ingestion_safety.py`, `errors.py`) are all untouched — confirmed via `git diff --stat` showing exactly the four modified files plus one new test file listed above.

### Phase 1.6 — Structured error response format across all endpoints

- **Scope determined from the roadmap's own text** (§37 item 1.6: "Structured error response format across all endpoints"; §21 API Strategy, verbatim: "Errors follow a single shape: `{"error": {"code": "...", "message": "...", "details": {...}}}`"). No dedicated backlog (§45) row exists for this item -- unlike every other Phase 1 milestone, 1.1-1.5 -- so its DoD is defined only by §37's title and §21's literal shape; there is no numeric/behavioral detail beyond that to under- or over-fit.
- **IN scope (implemented)**: a new `codepulse/api/errors.py` module with two global FastAPI exception handlers, registered once (`install_error_handlers(app)`) -- one for `HTTPException` (covers every existing 401/403/404/409/429/501/400 raise site, none of which needed to change), one for `RequestValidationError` (FastAPI's own automatic 422s), plus a catch-all `Exception` handler (500s, logged server-side via `logger.exception`, never leaking the real exception text/traceback to the client). The rate-limit middleware's own 429 (Phase 1.4, previously built as an ad-hoc `{"detail": ...}` dict directly, not raised as an `HTTPException`) was updated to call the exact same shared `error_json_response` helper the exception handlers use, so the envelope-building logic is never duplicated between the two call sites.
- **OUT of scope (explicitly NOT implemented)**: rewriting any error's status code or message wording (this milestone reshapes existing responses, it does not redesign what they say); MCP's own distinct, flatter error shape (roadmap §13: `{"error": "code_string", "message": "..."}`, no "details" -- a different section's requirement for a surface, MCP/Phase 5, that does not exist yet); a security test suite (Phase 1.7).
- **Design decisions made explicitly, not inferred from later milestones**:
  1. **`code` is derived deterministically from the HTTP status via Python's own `http.HTTPStatus` enum** (`HTTPStatus(404).name.lower()` -> `"not_found"`), not an invented per-endpoint string table -- every status code already in use (and any added later) maps correctly without `codepulse/api/errors.py` needing to know about it specifically.
  2. **`details` carries real, already-computed information where it exists, empty `{}` otherwise -- never fabricated.** Currently populated in exactly two cases: the rate limiter's real `retry_after_seconds` (the *same* value already used for the `Retry-After` header since Phase 1.4, not a second independently-computed number) on 429s, and the real Pydantic validation error list on 422s.
  3. **A genuinely unhandled exception (500) never leaks its real message/traceback to the client** -- `message` is the generic, fixed string "Internal server error"; the real exception is logged server-side only (`logger.exception`), matching how this project already treats other server-internal failure information. Verified this really works (not just reasoned about): a deliberately-broken route body was exercised via `TestClient(app, raise_server_exceptions=False)` and confirmed to return a clean structured 500 with no leaked text -- `raise_server_exceptions=True` (Starlette's TestClient default) intentionally re-raises the *original* exception to the calling test code even when an app-level handler already produced a clean response (a testing-visibility feature, not a production behavior), so tests that want to *inspect* the 500 response body must explicitly opt out of that default, which the one test needing it does.
  4. **The rate-limit middleware needed its own explicit fix, not just the global `HTTPException` handler.** Starlette's `ExceptionMiddleware`/`ServerErrorMiddleware` (which dispatch to `@app.exception_handler(...)` registrations) sit *inside* (closer to routing than) a custom `@app.middleware("http")` function in the stack ordering that matters -- an exception raised from *inside* such custom middleware is never seen by those dispatchers, so a plain `raise HTTPException(...)` there would never have reached the new handlers. Both call sites use the same `error_json_response` helper instead, avoiding a second, drifting implementation of the envelope shape.
- **Architecture rule preserved, with a deliberate placement note**: `codepulse/api/errors.py` lives *inside* `codepulse/api/` (unlike `auth.py`/`jobs.py`/`rate_limit.py`/`ingestion_safety.py`, which are top-level modules reusable by a future CLI/MCP surface) -- this is a REST-HTTP-response-shape concern specifically (§21's envelope), not a capability those other surfaces would reuse: MCP has its own, different error shape (§13), and the CLI never returns HTTP responses at all. `IndexingEngine`/`codepulse/indexer/`, `codepulse/storage/db.py`, `codepulse/auth.py`, `codepulse/jobs.py`, and `codepulse/ingestion_safety.py` were not touched.
- **Test impact was small and fully audited before implementing**: a project-wide search found only 2 existing test assertions anywhere that checked the old `{"detail": "..."}` shape directly (`tests/test_ingestion_safety_endpoint.py`, `tests/test_rate_limit_middleware.py`) -- both updated to check the new `error.message`/`error.code`/`error.details` path instead, with no change to what they actually verify. No test anywhere relies on an unhandled exception propagating through `TestClient` (verified via a project-wide `pytest.raises` search before adding the catch-all 500 handler), so that addition carried no regression risk.

### Phase 1.5 — Ingestion safety: path allow-list, SSRF check, size caps

- **Scope determined from the roadmap's own text** (§37 item 1.5; §15 Security Architecture's verbatim "Repository-ingestion safety (the dangerous endpoint)" paragraph: local-path allow-listing + traversal/symlink rejection, git-URL scheme validation + SSRF host check + size/file-count cap "before beginning a full clone"; §15's "Resource limits: max files per repo, max file size parsed..."; backlog B10, DoD "Path traversal / SSRF / oversized-repo attempts rejected with tests proving it"):
  - IN scope (implemented): a new top-level `codepulse/ingestion_safety.py` module -- `validate_local_path` (resolves symlinks/`..`, rejects anything outside a configured allow-list) and `validate_git_url` (scheme + resolved-host SSRF check), both wired into `POST /v1/repositories/index` as synchronous, pre-job checks; a file-count cap and a per-file size cap, both enforced inside `IndexingEngine.index_directory()` (see design decision 5 below for why); three new `CodePulseConfig` fields (`ingestion_allowed_roots`, `ingestion_max_files_per_repo`, `ingestion_max_file_size_bytes`).
  - OUT of scope (explicitly NOT implemented, reserved for later milestones or never assigned to this one at all): actually cloning/fetching a git repository (see design decision 1 below -- this codebase never had that capability, and no sprint item assigns it a milestone); request-body size caps (roadmap §15 lists this as a separate, server/ASGI-layer resource limit, not application code this milestone adds); a global/per-tenant concurrent-job cap (Phase 1.3 already added a *per-repository* advisory lock; §15's "per tenant" wording describes a distinct, unrequested control); a structured `{"error": {...}}` envelope (Phase 1.6); a dedicated security test suite (Phase 1.7).
- **Design decisions made explicitly, not inferred from later milestones**:
  1. **No git-URL fetching was invented.** Grep-confirmed: this codebase has zero git-clone/network-fetch code anywhere (no `subprocess`, `GitPython`, or clone logic). `IndexRepoRequest.source` (`"local"`/`"github"`/`"gitlab"`) has always been accepted but never branched on -- every prior phase silently mis-treated a git URL as a local path, indexing zero files while claiming "queued." Building real git-URL cloning is a much larger, unrequested feature no sprint item assigns a milestone to. What 1.5 *does* own, literally, is the "SSRF check" -- so `validate_git_url` is implemented and tested as a real, standalone safety primitive (ready for whenever a real fetch path exists), and the endpoint now honestly rejects a non-local `source` (after still validating the URL for safety first) with HTTP 501, rather than continuing the silent mis-processing.
  2. **`ingestion_allowed_roots` defaults to `[]` = unrestricted**, the opposite convention from `cors_origins` (which defaults to deny-all). This is deliberate, not an inconsistency: this endpoint acts on behalf of the local user who already has filesystem access to their own machine (CLAUDE.md: "Local mode is the default"), and the roadmap's own promised zero-configuration experience ("`codepulse index .` works with zero external infrastructure") would break if ingestion required allow-list configuration before any use. The interesting case for enforcing a strict allow-list is a server/team deployment exposing this API beyond localhost with a key untrusted parties might hold -- exactly §15's own stated concern, and exactly when an operator would configure the setting.
  3. **Traversal and symlink-escape rejection share one mechanism**: `Path(path).resolve()` (which both collapses `..` segments and follows symlinks) followed by a containment check against the resolved allow-list roots. No separate "reject literal `..` in the string" logic was written, because resolving first and checking containment catches both attack shapes identically and is simpler than pattern-matching the raw string.
  4. **File-count/file-size caps live inside `IndexingEngine.index_directory()`, not at the API boundary as a synchronous pre-flight check.** The file list they check against is only available after the discovery walk `index_directory()` already performs; duplicating that exact walk at the API layer just to pre-count would be wasteful and is exactly the kind of "second identity system"/duplicated-logic this project's established house style avoids (see `codepulse/ingestion_safety.py`'s module docstring). Consequence: a file-count violation surfaces as a **failed job** (poll `GET /v1/jobs/{job_id}`), not a synchronous 4xx like the allow-list/SSRF checks -- a deliberate, documented split between "known before any work starts" (checked synchronously) and "only discoverable once the directory has been walked" (checked as part of the job, surfaced via the existing Phase 1.3 job-failure path). A single oversized file is *skipped* (logged, not fatal), reusing the exact per-file error-tolerance pattern already established for malformed/unparseable files.
  5. **`codepulse/indexer/engine.py` IS modified by this milestone** -- a deliberate departure from Phases 1.2-1.4's "IndexingEngine untouched" pattern, and called out explicitly here rather than silently. File-count/size limits are genuine indexing-pipeline resource-safety concerns (the file list and each file's bytes are only known inside the discovery/parse loop itself), the same category as the engine's own pre-existing "no silent pseudo-embedding fallback" and "embedding model unavailable -> fail explicitly" invariants (§17) -- not an HTTP/auth-coupling violation of CLAUDE.md §3, which is specifically about authentication, not general resource safety. `IndexingEngine` still has zero knowledge of jobs, auth, or rate limiting.
- **Architecture rule preserved otherwise**: `codepulse/ingestion_safety.py` is a new top-level module (not under `codepulse/api/` or `codepulse/indexer/`), mirroring `codepulse/auth.py`/`codepulse/jobs.py`/`codepulse/rate_limit.py`'s placement.

### ⚠️ Incident during migration verification (Phase 1.3, found and fully remediated in that session -- kept here verbatim as accurate project history, not touched by Phase 1.4 or 1.5)

While running an ad-hoc Python one-liner to sanity-check new routes (`import codepulse.api.app as app_module; ...`), that import's module-level `storage_manager = StorageManager()` executed against the **default** `db_url` (`sqlite:///codepulse.db`, the real database) because the command was run without a `CODEPULSE_DB_URL` override. `StorageManager.__init__` unconditionally calls `Base.metadata.create_all(bind=self.engine)` **alongside** Alembic -- an already-documented, pre-existing piece of technical debt -- which silently created the new `index_jobs` table directly on the real `codepulse.db`, bypassing Alembic entirely and leaving `alembic_version` stale.

**Caught immediately** when applying the real Phase 1.3 migration to a disposable copy of `codepulse.db` failed with `table index_jobs already exists`. **Verified before remediating**: the accidentally-created table's schema was byte-for-byte identical to the migration's own definition (expected, since `create_all()` uses the exact same SQLAlchemy model), empty, and no pre-existing data was touched. **Remediated** via `stamp_database(revision="de22df2fc3ce")` -- Alembic's own non-destructive mechanism for tracking an already-correct schema -- applied to the disposable copy first, then identically to the real database. **No data was lost.**

**Lesson re-applied in both Phase 1.4 and Phase 1.5**: `codepulse.api.app` was again imported ad-hoc for sanity checks in both sessions, without an isolated DB URL. In neither case did this matter, because neither milestone added a new model to `codepulse/storage/db.py` -- `create_all()` had nothing new to create either time -- and the real `codepulse.db` was explicitly re-verified unchanged (schema and every row count) immediately afterward in both sessions.

- **New from Phase 2.2 (a necessary, disclosed, verified design adjustment):** `VectorIndex`'s underlying `sqlite3.Connection` is constructed with `check_same_thread=False`, since FastAPI/Starlette's shared threadpool means the same `IndexingEngine`/`VectorIndex` instance can legitimately be called from more than one OS thread across its lifetime -- verified experimentally (a real cross-thread write-then-read round trip) to behave correctly for this codebase's actual usage pattern. This avoids a new hard-crash mode Phase 2.2 would otherwise introduce (the pre-existing NumPy/list implementation had no thread-affinity restriction); it is not a claim of full concurrent-write safety, matching the codebase's existing (unchanged) lack of locking around `bm25_index`/`vector_index`.

**Blockers:** none currently known for starting Phase 2.3.
