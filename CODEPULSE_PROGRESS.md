### Phase 3.5 — Local BFS incremental graph update

**Scope, quoted from the roadmap and held to strictly**: §37 item 3.5, literally *"Local BFS incremental graph update"*; §9's "Call graph updates" section: *"rather than rebuilding the whole graph, recompute only edges whose *source* symbol is in the changed set, plus a local BFS one hop out to catch edges whose *target* changed (a symbol being renamed/deleted must have inbound edges from unrelated files corrected too)."*

- **Two distinct layers, only one of which this milestone touches**: the IN-MEMORY call graph (`CallGraphBuilder`, `self.call_graph`) is already fully rebuilt from merged/cached parse data every run (Phase 3.1's own design) -- cheap (no embedding involved), and left completely unchanged by this milestone. §9's actual ask operates one layer down, at the DURABLE `CallEdge` persistence step: **which DB rows get touched**, not how the in-memory graph is computed. This distinction is made explicit in code comments at every relevant site so a future reader doesn't conflate the two.
- **New `IndexingEngine._persist_call_graph_edges`** (`codepulse/indexer/engine.py`), replacing the prior unconditional "append every in-memory edge every run" block that every milestone since Phase 3.1 has pointed at this one to fix:
  - **Full run**: deletes every existing `CallEdge` row for `repo_id` (now possible at all only because the repository-isolation fix gave `CallEdge` a `repo_id` to scope by), then inserts the complete fresh set -- a full, correct, one-time replace, mirroring `BM25Index.remove_repo`'s existing Phase 2.1 pattern.
  - **Incremental run**: a genuinely surgical update. (1) Deletes existing rows whose `(source_file, source_symbol_name)` is in `changed_symbol_keys` (the source-side half of §9's algorithm). (2) **"Local BFS one hop out"**: queries the remaining rows for this repo whose `(target_file, target_symbol_name)` is in `changed_symbol_keys` -- i.e. OTHER, unrelated symbols' edges pointing at something that just changed, was renamed, or disappeared -- collects their own `(source_file, source_symbol_name)` as `one_hop_keys`, and deletes those too. (3) Inserts every edge from the fresh in-memory `self.call_graph.edges` whose source is in `changed_symbol_keys | one_hop_keys`. A symbol untouched by either step keeps its existing, already-correct rows exactly as they were -- no unnecessary rewrite, no accumulation.
  - Correctness of step (2)/(3) depends on the in-memory graph being COMPLETE even for files not reparsed this run -- already guaranteed by Phase 3.1's own cache-completeness design (`self.parse_results`) plus `_plan_incremental_run`'s existing "no in-memory call graph cached yet" restart-safety guard, both reused as-is, not modified.
- **`changed_symbol_keys` computation, threaded through THREE existing methods that each already computed the relevant identities internally but previously discarded them**: `_purge_stale_entries` (deleted files' symbols), `_rekey_renamed_files` (a renamed file's symbols' OLD identity -- the literal "renamed... must have inbound edges... corrected" case from §9's own parenthetical), and `_diff_and_purge_file_symbols` (symbols that disappeared within a still-existing, modified file) now all return the `(file_path, symbol_name)` keys they identify, accumulated in `index_directory` into `removed_symbol_keys`. Combined with `{(sym.file_path, sym.name) for sym in all_symbols if id(sym) not in unchanged_symbol_ids}` (every genuinely new-or-changed symbol under its CURRENT identity -- stable across a body-only change), this gives the complete, correct `changed_symbol_keys` set passed to `_persist_to_db` -> `_persist_call_graph_edges`. `_doc_ids_for_file` (the shared helper these three methods already called) was extended to return each symbol's `(file_path, name)` alongside the doc_ids it already computed, avoiding a second DB query.
- **What was verified, directly, not just inferred from the algorithm's design**: 8 new engine-level integration tests in `tests/test_call_graph_incremental_update.py`, most importantly a DIRECT reproduction of §9's own named scenario, in BOTH halves of its literal "renamed/deleted" wording -- a symbol (`helper()`) disappears from a still-existing file (`lib.py`), and separately its file is RENAMED (`lib.py` -> `library.py`) -- while an entirely UNCHANGED file (`service.py`, never reparsed this run, confirmed via `total_files`) still calls it in its own unmodified source; its existing `CallEdge` row is found via the local BFS one hop out and its `confidence` is correctly corrected from `"high"` to `"unresolved"` in every case (the call site is real and unchanged, so the edge itself must still exist -- only its resolution correctness changes). The same correction is verified for a whole-file deletion too. Also verified: a full re-index REPLACES rather than duplicates a repo's edges; an unrelated symbol's row is left with the SAME row id (not deleted+recreated) when nothing about it or its callees changed; a changed symbol's own source-side edges are correctly recomputed to a NEW call target; repeated incremental edits to the same symbol never accumulate duplicate edges; an empty changeset touches zero rows.
- **What was explicitly NOT touched, and why** (deliberate, disclosed scope boundaries): the in-memory call graph's own restart-survivability (`self.parse_results`/`self.call_graphs`, lost on a process restart, with `_plan_incremental_run`'s existing guard forcing a full run in that case) -- unchanged by this milestone; this fixes the DURABLE table's update strategy, not the in-memory cache's durability, and no roadmap item currently claims to fix that. Extending the multi-hop `get_callers`/`get_callees` to carry confidence or bucket depth (Phase 4.2's territory, disclosed since Phase 3.4). A symbol whose `start_line` shifts without a name/type change is still not recognized as identity-stable by the EXISTING `(file_id, name, start_line)` Symbol natural key (Phase 3.2/3.3's own disclosed, unrelated limitation) -- this milestone's `changed_symbol_keys` correctly follows whatever that key produces, it doesn't change it.
- **No database migration** -- `CallEdge.repo_id` already exists (added by the repository-isolation fix); this milestone is pure application logic using it.

### Phase 3.4 — CallEdge.confidence scoring

**Scope, quoted from the roadmap and held to strictly**: §37 item 3.4, literally *"CallEdge.confidence scoring"*; §11: *"every `CallEdge` should carry a `confidence` field — `high` when resolved through an explicit import mapping to a known file+symbol, `low` when resolved only by bare-name match against same-file symbols, `unresolved` when the callee couldn't be matched to any known symbol at all. This directly addresses the false-positive risk found in §3.5, and it's a **cheap** addition (the resolution logic already distinguishes these cases internally in `CallGraphBuilder._build_graph`; it just needs to be surfaced rather than silently discarded)"*; §29 Data Model: *"`CallEdge` | Yes (rename from `DependencyModel`, add `confidence`) | §11"*; §42 Risk Register: *"Call graph false positives | Medium | Medium | Confidence scoring surfaced to callers (§11), not hidden."*

- **Rename, per §29's explicit target entity name**: `DependencyModel` → `CallEdge` (table `dependencies` → `call_edges`, its two indexes renamed to match what `index=True` on a model actually named `call_edges` would auto-generate). Migration `f6e481353553`: purely a rename + one new nullable column, zero row-data loss (verified on a disposable copy: upgrade AND downgrade both correct, all 528 pre-existing rows preserved exactly either way).
- **Confidence computation, exactly matching §11's own three-tier definition** (`codepulse/parser/graph.py`, `CallGraphBuilder._build_graph`): `"low"` for a same-file bare-name match (the literal ambiguity §3.5's audit finding names — two unrelated classes defining a same-named method in one file would be conflated here); `"high"` for a callee resolved via an explicit import mapping to a target file **AND** confirmed present in `ImportResolver.symbol_index` as an actual extracted symbol there (not merely "some file was found that matches the import path"); `"unresolved"` for a true external call (no local match, no import match) **and** for an import that resolved to a real file but could not confirm the exact symbol in it (a wildcard import, a re-exported alias, or similar) — deliberately NOT falling back to `"low"` for that last case, since `"low"` is defined as a same-FILE match and this is cross-file; overclaiming confidence there would be worse than honestly saying `"unresolved"`.
- **A previously dead structure put to real, intended use**: `ImportResolver.symbol_index` (a `(file_path, symbol_name) -> Symbol` lookup) has existed since this class's very first version but was never read by anything anywhere in the codebase until this milestone — a strong signal it was originally built for exactly this "confirm a known file+symbol, not just a known file" check, never wired up before now.
- **Every value threaded through the full pipeline, not just computed and discarded**: `CallGraphEdge` (`codepulse/models.py`) gained a `confidence: str = "unresolved"` field; `IndexingEngine._persist_to_db` now passes `edge.confidence` into each persisted `CallEdge` row; `GET /v1/symbols/{id}` (`codepulse/api/app.py`) now includes `"confidence"` in every `called_by`/`calls` item — directly satisfying §42's "surfaced to callers, not hidden" mitigation and matching §12's own shown JSON shape (`{"symbol": ..., "file": ..., "confidence": "high"}`) for the (later, Phase 5) agent context endpoint.
- **`confidence` is nullable, honestly, per CLAUDE.md's "no fabricated metrics" rule**: rows persisted before this migration have no historical resolution-path information to reconstruct, so they show `confidence: null` in every API response and DB row until their repository's next re-index recomputes real values -- never backfilled with a guessed tier.
- **A THIRD occurrence of the `StorageManager.create_tables()`-alongside-Alembic incident, this time with a real-data-movement twist**: applying the migration to the real `codepulse.db` hit `there is already another table or index with this name: call_edges` -- a `StorageManager()` had been constructed against the real DB at some point after `db.py`'s `CallEdge`/`call_edges` rename was written (traced to this session's own ad-hoc `import codepulse.api.app` sanity-check command, whose module-level `storage_manager = StorageManager()` uses the real DB by default -- the exact same root cause as the Phase 1.3 and Phase 3.1 incidents), silently `create_all()`-ing an EMPTY `call_edges` table with the new schema while the real, populated `dependencies` table (528 rows) sat untouched alongside it. Unlike the previous two incidents (fixable by `stamp_database` alone, since nothing needed to move), this one could NOT be resolved by stamping -- the migration's job is to RENAME `dependencies` into `call_edges` and move its 528 real rows there, and `call_edges` already existing (empty) would block that rename outright. **Remediated by**: verifying the accidental table was genuinely empty and schema-identical to what the migration would produce, backing up the real DB, dropping the accidental empty `call_edges` table, then running the real migration normally. Real `codepulse.db` confirmed unchanged in substance before and after (`repositories=1, files=18, symbols=128`, `call_edges` -- ex-`dependencies` -- `=528`, etc.); the backup was deleted once the result was verified.
- **What was explicitly NOT done** (deliberate scope decisions matching neighboring roadmap items, disclosed in full above and in Known Issues/Current Risks, not oversights): extending the multi-hop, BFS-based `get_callers`/`get_callees` (used by the CLI's `impact` command and the API's impact-analysis endpoint) to carry or aggregate confidence across a multi-edge path -- that reads as roadmap item 4.2's own "direct vs. transitive bucketing" territory, a different, later milestone, not 3.4's single-edge scope; recomputing only the edges touching changed symbols (avoiding the pre-existing, disclosed Phase 0.4 accumulation-on-every-re-index gap) -- explicitly roadmap item 3.5's "local BFS-based incremental graph updates," not 3.4's; correcting a renamed file's stale `CallEdge` rows (Phase 3.2's own disclosed, still-open finding) -- same reason.
- **What was verified**: 7 new focused tests -- 4 in `tests/test_graph.py` (each of the three confidence tiers individually, including the "resolved file but unconfirmed symbol still isn't `high`" case) and 3 in the new `tests/test_call_edge_confidence.py` (persisted `CallEdge` rows carry the correct computed confidence end-to-end through `IndexingEngine`, `GET /v1/symbols/{id}` surfaces it correctly for both a caller and a callee, and a pre-migration-style row with no confidence value surfaces as `null`, never fabricated). Full suite **358 passed, 1 skipped** -- exactly 351 + 7. Real `codepulse.db` migrated and verified as described above.

### Phase 3.3 — Symbol-level body_hash comparison to skip unchanged embeddings

**Scope, quoted from the roadmap and held to strictly**: §37 item 3.3, literally *"Symbol-level body_hash comparison to skip unchanged embeddings"*; §9: *"within a changed file, compare `body_hash` per extracted symbol against the previous snapshot's symbols (matched by `(name, type)` first, falling back to signature similarity if the name changed — a simple heuristic, not a semantic diff). Unchanged symbols skip re-embedding and re-chunking entirely — this is the single biggest cost saver on incremental runs"*; §8's pipeline diagram: *"Chunking (only for new/changed symbols, by body_hash comparison)"* / *"Embedding (only chunks whose body_hash changed)."*

- **A real, necessary architectural consequence discovered while planning this milestone, before any code was written**: Phase 3.1's existing `_purge_stale_entries` purges a MODIFIED file's lexical/vector doc_ids at FILE granularity (every symbol in the file, unconditionally) BEFORE the parse loop re-adds them. If this milestone's skip-decision simply left an "unchanged" symbol's doc_id untouched while `_purge_stale_entries` had ALREADY wiped it moments earlier for the whole file, that symbol's search entry would be gone forever with nothing left to put it back (since skipping means no re-add either) -- a real, would-be data-loss regression if shipped as originally structured. **Fixed by restructuring**: the file-level purge for MODIFIED files (and a rename's new path) was removed from the pre-parse-loop pass entirely -- `_purge_stale_entries` is now called ONLY for genuinely `deleted_relpaths` (whole files gone). A NEW, SYMBOL-granular replacement, `_diff_and_purge_file_symbols(repo_id, rel_path, new_symbols)`, runs per-file INSIDE the parse loop, immediately after that file is parsed, and purges only the doc_ids of symbols that actually changed or disappeared -- leaving untouched symbols' doc_ids (and DB rows) completely alone from start to finish.
- **New `IndexingEngine._diff_and_purge_file_symbols`** (`codepulse/indexer/engine.py`): for a given file, compares its freshly parsed symbols against the EXISTING, durable `SymbolModel` rows for that file (if any), matched by `(name, start_line)` plus a `type` equality check -- **the exact same natural key `_persist_to_db`'s own Symbol upsert already uses**, a deliberate, disclosed scope choice (see the scope-fork bullet below), NOT the broader, start_line-independent `(name, type)` matcher §9's text also describes. Classifies each symbol as: **unchanged** (matched, same `body_hash` -- returned to the caller as `{id(sym), ...}` so chunking/embedding/BM25-readd can be skipped for it); **changed** (matched, different `body_hash` -- its stale doc_ids are purged now, so the pipeline's normal re-chunk/re-embed/re-add for it lands cleanly); **disappeared** (an existing row with NO matching new symbol at all -- deleted from the file, or renamed to a different name WITHIN the file -- its `SymbolModel` row is deleted directly, cascading to `Embedding`, and its doc_ids purged); **new** (no existing row -- untouched, handled by the normal pipeline as always). A brand-new file (no existing `FileModel` row) or a symbol whose `start_line` shifted (not matched by this key) safely falls through to the pre-existing, unchanged behavior for that case.
- **A genuine, previously-disclosed, long-standing gap closed as a necessary side effect, not a separate fix**: the "disappeared" case above directly closes what `_persist_to_db`'s own docstring has said since Phase 0.4 -- *"this mirrors Phase 0.4's decision not to delete stale Symbol rows... real stale-data cleanup is Phase 3"*. A symbol removed from (or renamed within) a still-existing file now has its stale row and embedding actually deleted, not silently orphaned forever. Regression-tested (`test_disappeared_symbol_within_a_modified_file_is_cleaned_up`).
- **`index_directory()` wiring**: the parse loop now calls `_diff_and_purge_file_symbols` for every file being parsed during an INCREMENTAL run (skipped for a rename's new path -- see below), accumulating a run-wide `unchanged_symbol_ids: set[int]`. For each symbol in that set: `self.chunker.chunk_symbol(sym)` is never called (no chunks -> no embedding -> no `vector_index.add_batch` call for it -- the actual expensive work §9 calls "the single biggest cost saver"), and the BM25 population loop's `self.bm25_index.add_symbol(...)` call is also skipped for it. `self.symbols_by_id`/`self.symbol_repo_map` are still refreshed for every symbol regardless (cheap, keeps them pointing at the freshest parsed object) -- only the two genuinely expensive/duplicate-risking calls are skipped.
- **A real, disclosed scope fork, resolved the same way as Phase 3.2's own (a deliberate, conservative choice, not silently picked)**: this milestone applies the skip optimization ONLY during incremental runs, and ONLY via the SAME `(name, start_line)`-based matching `_persist_to_db` already uses -- NOT §9's fuller `(name, type)` (start_line-independent) matcher with a signature-similarity fallback. A symbol whose `start_line` shifts because unrelated code above it in the file changed is therefore NOT recognized as unchanged and gets a fresh re-chunk/re-embed (with a fresh id if `_persist_to_db`'s own key also misses it) -- exactly today's pre-existing Phase 0.4 behavior for that case, not a new regression, but also not the fuller cost-saving §9 describes. Building the fuller `(name,type)` matcher (which would ALSO have let Phase 3.2 preserve ids across a rename-with-edit that shifts a symbol's line) is a disclosed, deferred enhancement -- not built now, consistent with the Phase 3.2 precedent of preferring the conservative, already-correct-by-construction option.
- **A second deliberate scope boundary**: the skip optimization is NEVER applied to a file that was renamed this run (pure or with edits) -- a rename changes every symbol's doc_id string (which embeds the file path) regardless of body content, so "leave the doc_id untouched" cannot apply; `_rekey_renamed_files` (Phase 3.2) already purges those doc_ids in full and the file is fully re-chunked/re-embedded, unaffected by this milestone. Reusing a durably-stored embedding vector under a renamed file's new doc_id (skipping the model call even though the doc_id itself must still move) is a disclosed, deferred enhancement, not built now. Regression-tested (`test_pure_rename_does_not_apply_the_symbol_skip_optimization`).
- **A third deliberate scope boundary**: the optimization is NEVER applied during a FULL (non-incremental) re-index. A full run's existing, unconditional `self.bm25_index.remove_repo(repo_id)` call (Phase 2.1/3.1) wipes every symbol's lexical document up front, so skipping any symbol's BM25 re-add during a full run would permanently lose it. Since `unchanged_symbol_ids` is only ever populated when `_diff_and_purge_file_symbols` is called, and that is only ever called during an incremental run, this is enforced by construction, not a runtime check. Regression-tested (`test_full_reindex_never_applies_the_symbol_skip_optimization`).
- **`index_directory()`'s return dict**: new `"symbols_skipped_unchanged": int` key, disclosing exactly how many symbols this run avoided re-chunking/re-embedding.
- **What was verified**: 5 new focused tests in `tests/test_incremental_indexing.py` -- an unchanged symbol within a modified file skips embedding (spied: the embedder is asserted to never see its text) and BM25 re-add, while a changed symbol in the SAME file still updates correctly and a third, untouched file's own symbol is unaffected; a disappeared symbol's row/embedding are actually deleted, not orphaned; a pure rename applies zero skips (locking in the Phase 3.2 boundary); a forced full re-index applies zero skips and still produces exactly the right number of lexical documents (no loss, no duplication); the in-memory call graph remains fully correct for a skipped symbol (edges are built from the complete parsed-symbol list, unaffected by the skip decision). Full suite **351 passed, 1 skipped** -- exactly 346 + 5. Real `codepulse.db` untouched throughout (no migration exists for this milestone to apply).

### Phase 3.2 — Rename/move detection + symbol re-keying

**Scope, quoted from the roadmap and held to strictly**: §37 item 3.2, literally *"Rename/move detection + symbol re-keying"*; §9: *"for git repos, use git's own rename detection (`git diff -M`) to map `(old_path → new_path)` and re-key existing `Symbol`/`Embedding` rows to the new path instead of delete+recreate — this preserves symbol IDs"*; Phase 3 DoD: *"renamed files retain their symbol/embedding history"*; §42 Risk Register: *"Rename/move detection incorrectly merges unrelated symbols | Low | Medium | Conservative matching heuristic (git rename detection + name/type match) with fallback to delete+recreate rather than a risky guess."* A full read-only audit (quoting all of the above, plus inspecting `SymbolModel`'s existing `(file_id, name, start_line)` natural key, `FileModel`'s `(repo_id, path)` key, `DependencyModel`'s plain-text `source_file`/`target_file` columns, and the existing BM25/Vector doc_id format) was performed and presented to the user BEFORE any code was written, per the user's own explicit instruction.

- **A real, disclosed scope fork surfaced by the audit, resolved by explicit user decision (not silently picked)**: re-keying `FileModel.path` in place fully satisfies "preserves symbol IDs" for a **pure rename** (git similarity `R100`, byte-identical content) — every symbol's `start_line` is unchanged, so the existing `(file_id, name, start_line)` key matches every row perfectly with zero new matching logic. For a **rename + content edit** (similarity `R50`-`R99`), a symbol whose own `start_line` shifts would not be matched by that key and would fall back to today's existing, already-disclosed Phase 0.4 behavior (a fresh id, old row orphaned — never cleaned up by any existing mechanism). The risk register's literal "name/type match" wording suggested 3.2 itself might need a start_line-independent `(name, type)` matcher to close that gap, but that reads like it overlaps with §9's own separate "Symbol-level change detection" section, which is 3.3's dedicated job. **Presented to the user as an explicit choice; the user chose file-level re-keying only** ("sufficient for this milestone") over building a `(name,type)` matcher now. This is the scope actually implemented.
- **`codepulse/git_diff.py` rewritten for rename detection**: `git diff -M --name-status` replaces Phase 3.1's `--no-renames` (an explicit, deliberate inversion of that milestone's own scope boundary — expected, roadmap-driven, not a regression). Parses `R<similarity>\t<old_path>\t<new_path>` status lines (3 tab-separated fields, unlike every other status) into a new `ChangeSet.renamed: list[tuple[str, str]]`. Uses git's own default 50% similarity threshold, unmodified — a move below that threshold is git's own plain delete+add, and this module does not override that judgment (directly matching the risk register's own mitigation: rely on git's rename detection, not a custom heuristic). Copy detection (`-C`) is deliberately NOT enabled — not named by the roadmap. `changed_or_added`/`total_changed` updated to include a rename's new path / count a rename as one changed unit.
- **New `IndexingEngine._rekey_renamed_files(repo_id, renamed_pairs)`** (`codepulse/indexer/engine.py`): for each `(old_path, new_path)`, finds the EXISTING `FileModel` row at `old_path`, computes its symbols' current (old-path-encoded) BM25/Vector doc_ids via a new shared helper (`_doc_ids_for_file`, factored out of `_purge_stale_entries` so both share the exact same doc_id-reconstruction logic), removes those stale doc_ids from both search indexes (doc_id strings embed the file path, so they go stale the moment the path changes even though nothing about the underlying rows needs to change), then updates the row's `path` column to `new_path` **in place** (a plain `UPDATE`, not delete+insert) — preserving `file_id` and therefore every associated `Symbol.id`/`Embedding.id` via the unchanged `file_id` FK. `new_path` is included in this run's `changed_relpaths` (via `ChangeSet.changed_or_added`) so it gets parsed normally immediately after — `_persist_to_db`'s existing File-upsert-by-`(repo_id, path)` lookup then finds the already-re-keyed row and correctly treats it as an update-in-place, not a fresh insert.
- **A real ordering bug found and fixed during wiring, not shipped**: `_purge_stale_entries` is also called (for genuinely modified/deleted paths) in the same `index_directory` block. Since a rename's `new_path` is included in `changed_relpaths`, and `_purge_stale_entries`'s *un-narrowed* input would have included it too, calling it AFTER `_rekey_renamed_files` would have immediately DELETED the very row just carefully re-keyed (a lookup by the now-current `new_path` would find and remove it) — silently undoing the whole point of re-keying on every single rename. **Fixed**: `_rekey_renamed_files` runs first, then `_purge_stale_entries` is called with `(changed_set - renamed_new_paths) | deleted_relpaths`, explicitly excluding renamed files' new paths. Regression-tested (`test_renamed_file_and_an_unrelated_addition_together` proves the symbol id survives when a rename and an ordinary add happen in the same commit).
- **Conservative fallback, per the risk register's own text**: if `_rekey_renamed_files` finds no existing row at `old_path` (e.g. it was excluded by `.codepulseignore` and never actually indexed, even though git still tracked and renamed it), it logs a warning and skips re-keying for that pair — `new_path` still gets indexed normally as a fresh file via the ordinary parse loop (it is already in `changed_relpaths` regardless). Regression-tested (`test_rekey_renamed_files_is_a_safe_no_op_when_the_old_path_was_never_indexed`).
- **`IncrementalPlan`** (dataclass): new `renamed: list[tuple[str, str]]` field. All existing `IncrementalPlan(...)` construction call sites in `_plan_incremental_run` were converted from positional to keyword arguments as part of this change — inserting `renamed` positionally before the pre-existing `reason` field would otherwise have silently rebound every one of the 9 existing call sites' `reason` string into the new `renamed` field. Caught and fixed before running any test.
- **`index_directory()`'s return dict**: new `"renamed_files": [{"old": ..., "new": ...}, ...]` key, mirroring the existing `"deleted_files"` key.
- **What was explicitly NOT done** (the resolved scope fork above, plus deliberate boundaries matching 3.3-3.5's own separate roadmap items): `(name, type)`-based, start_line-independent symbol matching for a rename that also edits content (explicit user decision, see above — left to whatever 3.3 builds for the general modified-file case, if anything); `DependencyModel` (call graph edge) rows recorded before a rename keep referencing the OLD path string — call graph edges are never deduped/corrected across ANY re-index (a pre-existing Phase 0.4 gap, not made worse in kind by renames specifically), and correcting inbound edges after a rename is explicitly §9's "Call graph updates" section, mapped to roadmap items 3.4/3.5, not 3.2; the in-memory `self.call_graph`/`self.call_graphs[repo_id]` (rebuilt fresh from `cg_parsed_files` each run, per Phase 3.1's own merge) IS correct after a rename since it's derived from the freshly re-parsed file under its new path — only the DURABLE `DependencyModel` rows carry old-path debris, and that table is already read live by `GET /v1/symbols/{id}` (`codepulse/api/app.py`), so this is a real, disclosed, pre-existing-in-kind limitation, not a new one; skip-re-embedding for a byte-identical pure rename was NOT implemented (the file still gets fully re-parsed/re-chunked/re-embedded like any other file in `changed_relpaths` — consistent with Phase 3.1's own established behavior that ANY re-parsed file is fully re-embedded regardless of which individual symbols actually changed; true embedding-skip is explicitly 3.3's job).
- **What was verified**: 9 new focused tests (3 in `tests/test_git_diff.py`: pure rename detected as rename — inverting Phase 3.1's own prior test, rename+small-edit still detected as a rename, a move below git's similarity threshold correctly falls back to delete+add, multiple renames together with an add; 6 in `tests/test_incremental_indexing.py`: pure rename preserves File/Symbol/Embedding ids, search results move to the new path with stale old-path doc_ids gone, a rename+content-edit updates the matched symbol's body in place while preserving its id, the defensive no-existing-row fallback, the in-memory call graph reflects the new path with the same edge count, and the ordering-bug regression test). Full suite **346 passed, 1 skipped** — exactly 337 + 9. No pre-existing test needed updating (no migration, no schema change). Real `codepulse.db` untouched throughout (confirmed via row-count/revision check before and after) — no migration exists for this milestone to apply.

### Phase 3.1 — Git-diff based incremental indexing

**Scope, quoted from the roadmap and held to strictly**: §37 item 3.1, literally *"Git-diff change detection (added/modified/deleted)"* — one item out of five in Phase 3's sprint list (§37: 3.1 this item, 3.2 rename/move detection + re-keying, 3.3 symbol-level body_hash comparison to skip unchanged embeddings, 3.4 `CallEdge.confidence` scoring, 3.5 local BFS incremental graph update). **Only 3.1 was implemented. 3.2-3.5 are NOT started, NOT inferred, and NOT silently absorbed** — in particular, a rename is deliberately detected as a delete+add (via `git diff --no-renames`), not as a rename, precisely so 3.2's job is not done here. §9 (Incremental Indexing Design) and §29 (Data Model, which explicitly lists `RepositorySnapshot` as `Yes (new) | Required for incremental indexing (§9) and crash-safe reads (§17)`) were also read in full and quoted verbatim before implementation.

- **New module `codepulse/git_diff.py`**: `is_git_repository`, `get_head_commit_sha`, `detect_file_changes(repo_path, since_commit) -> ChangeSet` (`added`/`modified`/`deleted` lists + `changed_or_added`/`total_changed` properties), all via the system `git` binary through `subprocess` (no new dependency). `GitDiffError` on any failure. Deliberately uses `--no-renames` in the underlying `git diff --name-status` call.
- **New DB model `RepositorySnapshotModel`** (`codepulse/storage/db.py`) + migration `c286d277ea21_add_repository_snapshot_model.py` (purely additive: one new table `repository_snapshots` + one index `ix_repository_snapshots_repo_id`; down_revision `de22df2fc3ce`). A run-history table (no natural-key `UniqueConstraint`, mirroring `IndexJobModel`'s own pattern) recording `repo_id`, `commit_sha` (nullable — `None` for a non-git repo run), `embedding_model`, `embedding_dim`, `indexed_at`. Does **not** implement §17's full crash-safe "always serve latest ready snapshot" read semantics — that is a broader, separate concern, disclosed as out of this milestone's scope, not silently expanded into.
- **New deletion capability on both search indexes** (required by 3.1's own literal "(deleted)" scope, not opportunistic cleanup — CLAUDE.md §12's "required by the current milestone" exception, used for the second time this session after Phase 2.5's k-limit fix):
  - `BM25Index.remove_docs(doc_ids)` (`codepulse/search/bm25.py`) — exact-term delete on Tantivy's `doc_id` field (empirically re-verified to work correctly on a TEXT field, not just the previously-verified integer `repo_id` field). Safe no-op for an unknown/never-indexed `doc_id`.
  - `VectorIndex.remove_docs(doc_ids)` (`codepulse/search/vector.py`) — required abandoning the old "rowid = list-index + 1" positional-arithmetic shortcut (broken once middle entries can be removed) for an explicit `_rowid_by_doc_id`/`_doc_by_rowid` dict-mapping design with a monotonic `_next_rowid` counter that is never decremented or reused — verified via a dedicated regression test that a freed rowid can never collide with a still-live one after a remove-then-re-add cycle.
- **New `IndexingEngine` methods** (`codepulse/indexer/engine.py`): `_plan_incremental_run(repo_path, repo_id) -> IncrementalPlan` implements §9's own "when a full re-index is still required" fallback list, in order: (1) `incremental_indexing_enabled=False` via config, (2) not a git repo / no commits, (3) **no in-memory call graph cached yet for this `repo_id`** (a guard this milestone added beyond §9's literal list — see below), (4) no prior successful git-backed snapshot, (5) embedding model/dimension changed since the last snapshot, (6) same commit as the last snapshot (still incremental, empty changeset — not a failure), (7) `git diff` itself fails, (8) more than `incremental_max_changed_file_fraction` (default 0.5, §9's own literal "50%" example) of previously-indexed files changed. `_purge_stale_entries(repo_id, relpaths)` removes a set of relpaths' durable `File`/`Symbol`/`Embedding` rows plus their lexical/vector index entries and in-memory caches — used for BOTH permanently-deleted files AND, critically, for **modified** files immediately BEFORE they are re-parsed (see the "modified-file duplication" fix below). `_record_snapshot(repo_id, repo_path)` records one `RepositorySnapshotModel` row after every successful run (full or incremental); a failure here is logged, not raised (a missing snapshot only ever forces the *next* run to safely fall back to full).
- **A real correctness gap, self-identified during wiring and fixed before this was considered done — NOT left as a known limitation**: `doc_id` is derived from `repo_id::file_path::symbol_name`, stable across a content-only change to an existing symbol. Without removing a modified file's OLD doc_id entries first, re-adding its freshly re-parsed symbols under the same doc_id strings would silently accumulate duplicate lexical/vector entries on every incremental run that touches a previously-indexed file. **Fixed**: `_purge_stale_entries` runs on the union of `changed_relpaths` (added+modified) and `deleted_relpaths` BEFORE the parse loop — a safe no-op for added files (no prior row exists), and correct staleness removal for modified files. Directly regression-tested (`tests/test_incremental_indexing.py::test_incremental_run_handles_added_modified_and_deleted_files_together` asserts exactly 3 live BM25 documents after a rename-like symbol change, not 4).
- **A second real correctness gap, also self-identified and fixed**: `IndexingEngine.index_directory`'s existing `self.bm25_index.remove_repo(repo_id)` call (Phase 2.1) unconditionally wipes every lexical document for the repo before re-adding `all_symbols` — correct for a FULL run (which re-adds everything), but would have silently wiped every *unchanged* file's lexical documents on an INCREMENTAL run (which only re-adds the changed subset, permanently losing lexical coverage for the rest). **Fixed**: this call is now gated on `not incremental_plan.is_incremental` — an incremental run relies on `_purge_stale_entries`'s already-precise per-path removal instead of a whole-repo wipe.
- **A third real correctness gap, also self-identified and fixed — the "fabricated metrics" risk**: `_persist_to_db` previously set `RepositoryModel.file_count`/`symbol_count` to `len(parsed_files)`/`len(all_symbols)` — correct on a full run (where those lists cover every file), but would have silently shrunk to just the changed subset's count on an incremental run, a direct violation of the "no fabricated metrics" invariant, and one that would also corrupt `_plan_incremental_run`'s own `prior_file_count` denominator (the >50%-changed-fraction check) on every subsequent run. **Fixed**: both fields are now set from a real `SELECT COUNT(*)` against `FileModel`/`SymbolModel` for the repo, after this run's upserts are flushed — identical result to the old approach on a full run, correct on an incremental one. Verified directly (`test_file_and_symbol_counts_reflect_true_totals_after_incremental_run`).
- **A fourth real gap, self-identified and fixed with a disclosed limitation**: an incremental run's `parsed_files` only covers the changed subset, so building `CallGraphBuilder(parsed_files)` from it alone would silently regress call-graph completeness (edges from every unchanged file vanishing from `self.call_graphs[repo_id]`) relative to every pre-Phase-3.1 (always-full) run. **Mitigated, not fully solved** (solving it properly is roadmap item 3.5's job, explicitly deferred): this engine's own `self.parse_results` cache (previously write-only, now repo-qualified as `"{repo_id}::{rel_path}"` — a required change since it is now load-bearing for the first time) is merged with this run's freshly parsed files to rebuild a complete-for-this-repo call graph on every incremental run. **Disclosed limitation**: `self.parse_results` is in-memory, not durable — after a process restart, a fresh engine has an empty cache, which is exactly why `_plan_incremental_run` also added the new "no in-memory call graph cached yet" fallback guard (item 3 in the ordered list above): it forces a full run whenever `repo_id not in self.call_graphs`, which is always true right after a restart, so the incomplete-merge scenario is never actually reachable in practice. Verified directly (`test_call_graph_remains_complete_across_an_incremental_run`, `test_falls_back_to_full_reindex_after_a_fresh_engine_with_no_cached_call_graph`).
- **New config settings** (`codepulse/config.py`): `incremental_indexing_enabled` (default `True`) and `incremental_max_changed_file_fraction` (default `0.5`, §9's own literal example), both with `CODEPULSE_*` env var mappings.
- **`index_directory()`'s return dict** now also carries `incremental` (bool), `incremental_reason` (the real, human-readable reason from `IncrementalPlan`), and `deleted_files` (the list of relpaths removed this run) — so a caller can see *why* a given run took the path it did, not just its file/symbol counts.
- **What was explicitly NOT done** (deliberate scope decisions, matching 3.2-3.5's own literal, separate roadmap items): rename/move detection and symbol re-keying (3.2) — a rename is deliberately delete+add; symbol-level `body_hash` comparison to skip re-embedding an unchanged symbol *within* a changed file (3.3) — a changed file's every symbol is currently re-chunked/re-embedded, even one whose own body didn't change (this milestone's cost saving is at the *file* granularity only, not the *symbol* granularity §9 describes as "the single biggest cost saver"); `CallEdge.confidence` scoring (3.4); local BFS incremental graph update (3.5) — this milestone's call-graph-completeness fix (above) is a best-effort, single-process-lifetime patch, explicitly NOT the durable, restart-safe incremental graph maintenance 3.5 will actually deliver. Also not done: §17's full crash-safe "always serve latest ready snapshot" read semantics (broader than this milestone); Dependency (call graph edge) row deduplication (still accumulates on every run, pre-existing Phase 0.4 limitation, unchanged); `VectorIndex`'s full-reindex repository-replacement idempotency gap (Phase 2.2, still open, unrelated to this milestone's incremental-specific `remove_docs` fix).
- **Real DB migration applied**: verified upgrade+downgrade on a disposable copy of `codepulse.db` first (schema correct; all existing data — repositories=1, files=18, symbols=128, dependencies=528 — untouched on upgrade; table cleanly removed, revision reverted on downgrade). Applying to the real `codepulse.db` via `run_migrations` hit `table repository_snapshots already exists` — inspection showed the table already existed (0 rows, schema byte-for-byte identical to the migration's own DDL) purely as a side effect of `StorageManager.__init__`'s pre-existing, already-documented `Base.metadata.create_all()`-alongside-Alembic behavior (a `StorageManager()` pointed at the real DB was constructed at some point after `RepositorySnapshotModel` was added to `db.py`, most likely by this session's own earlier ad-hoc sanity checks). **Remediated exactly like the identical Phase 1.3 incident**: `stamp_database(revision="c286d277ea21")` instead of re-running the DDL — non-destructive, and correct since the physical schema already matched. Real `codepulse.db` confirmed unchanged before and after: `repositories=1, files=18, symbols=128, dependencies=528, code_embeddings=0, api_keys=0, index_jobs=0`, plus the new `repository_snapshots=0`. A disposable backup copy (`codepulse.db.pre-phase3.1-backup`) was made before stamping and deleted after the stamp was verified successful.

- **A REAL, PREVIOUSLY-UNKNOWN BUG WAS DISCOVERED AND FIXED** while running this milestone's own benchmark -- the single most significant finding of Phase 2.5. `sqlite-vec`'s `vec0` KNN query enforces a hard limit of `k <= 4096` (a real constraint of the library itself, confirmed by its own error text: `"k value in knn query too large, provided 40000 and the limit is 4096"`). `IndexingEngine.search()`'s repository-scoped candidate-pool sizing (Phase 0.6, unchanged since) intentionally requests `top_k = len(vector_index.doc_ids)` -- the entire corpus -- so `_repo_filter`'s post-filtering is never starved. At realistic scale (the ~10K-file tier: 20,000 symbols → ~40,000 embedded chunks) this number now regularly exceeds sqlite-vec's own limit, and **every Phase 2.2 test used small corpora that never exercised this path** -- meaning any real, moderately-large-corpus repository-scoped semantic or hybrid search has been silently crashable (`sqlite3.OperationalError`) since Phase 2.2's commit (`9fb498a`), undetected until Phase 2.5's benchmark harness actually ran a realistic-scale scoped query. **Fixed** by clamping `top_k` in `VectorIndex.search()` (`codepulse/search/vector.py`) at `min(top_k, len(self.doc_ids), 4096)` -- the smallest number sqlite-vec itself will ever accept, applied defensively for every caller, not just the benchmark's own path. Judged squarely in-scope for this milestone (CLAUDE.md §12's own exception: "required by the current milestone") since the benchmark literally cannot produce numbers for the 10K/25K tiers without it -- not opportunistic cleanup.
  - **Disclosed trade-off of the fix, not silently glossed over**: capping at 4096 means a hypothetical, very large multi-repository deployment (a query result set genuinely dominated by >4096 higher-scoring chunks from OTHER repositories before this repository's own best candidates appear in the global ranking) could in principle see `_repo_filter` return fewer than `limit` results for the target repository. This is the same class of approximation the existing "pull the whole corpus" heuristic already was (never a formally-guaranteed-complete strategy), not a new kind of incompleteness introduced by this fix -- and is unreachable within this milestone's own single-repository-per-tier benchmark. Not investigated or engineered around further; flagged as a real, open risk for a genuine multi-tenant, very-large-corpus deployment.
  - New regression test: `tests/test_sqlite_vec_semantic_index.py::test_top_k_beyond_sqlite_vec_own_hard_limit_does_not_crash` -- reproduces the exact crash scenario (4200 vectors, `top_k=4200`) and proves it now returns a real, correctly-ordered, capped result set instead.
- **The benchmark harness itself** (`tests/benchmark/harness.py`): pure, reusable logic -- a deterministic fixture-repo generator (`generate_fixture_repo`, varied realistic identifiers from a verb/noun vocabulary, not degenerately repeated text), a real percentile computation (`percentile`, nearest-rank + linear interpolation, no library dependency), and `measure_search_latency` (real `time.perf_counter()` timings over repeated real search calls). **Deliberately NOT a pytest test file** (no `test_` prefix, not auto-collected) -- a real multi-tier run takes real wall-clock minutes, and has no business slowing down the routine `pytest -q` full-suite check every other milestone in this project has relied on, matching §20's own explicit "not every PR -- too slow" framing. `tests/test_benchmark_harness.py` (12 tests, part of the routine suite) unit-tests the harness's own pure functions with fast, tiny synthetic inputs -- fixture-file validity (real parseable Python with real docstrings), determinism, lexical diversity, percentile correctness, latency-measurement call-counting.

### Phase 2.2 — Embedded (sqlite-vec-backed) ANN vector index

- **Scope determined from the roadmap's own text** (§36 Phase 2's objective, unchanged from Phase 2.1: *"replace brute-force search internals without changing the ranking contract"*; §37 item 2.2: *"Embedded ANN vector index adapter behind existing VectorIndex call sites"*; §45 backlog B13: *"Embedded ANN vector index... `search/vector.py` replacement... Dependency: B4... DoD: Same as above for semantic search"* [B12's benchmark half is Phase 2.5's job, not this milestone's — no latency numbers are reported here]; §7 Storage Decision: *"a local vector index (e.g., `sqlite-vec` or a persisted HNSW structure via `hnswlib`, avoiding pgvector's Postgres dependency entirely for local mode)"*).
- **Dependency selection was forced by the real development environment, not silently chosen.** §7 names two candidate libraries without picking between them. `hnswlib` was attempted first (`pip install hnswlib`) and **failed**: PyPI carries only a source distribution for this platform/Python combination (no prebuilt wheel for CPython 3.11 / win_amd64), and building it requires a C++ compiler (`Microsoft Visual C++ 14.0 or greater`) that is not installed on this machine — confirmed by a direct, failed install attempt, not assumed. Installing system-level build tooling was judged out of scope for this milestone. `sqlite-vec` (0.1.9) was tried next and **installed cleanly** (a prebuilt `win_amd64` wheel exists) — used instead. This is disclosed here and in `codepulse/search/vector.py`'s own module docstring, not silently substituted.
- **A real, material nuance about the library actually used, verified experimentally rather than assumed**: `sqlite-vec` 0.1.9's `vec0` virtual table performs an **exact** (brute-force) distance computation over every stored vector at this version — it is not yet an approximate/graph-based nearest-neighbor structure the way `hnswlib`'s HNSW algorithm is. Confirmed by direct testing: every query tried against the new adapter produced results *identical* to the pre-Phase-2.2 NumPy implementation, not merely similar. This still satisfies §7's literal wording (`sqlite-vec` is one of its two explicitly named options) and is a genuine embedded, compiled-native vector index rather than a pure-Python/NumPy one — but "ANN" in §36/§37's own wording is, at this specific library version, not literally approximate. A beneficial side effect: retrieval remains fully deterministic (CLAUDE.md §4's permanent invariant) as a direct, simple consequence, which an approximate structure would not guarantee as straightforwardly.
- **The real, installed Python binding (`sqlite_vec` 0.1.9) was directly introspected and round-trip-tested before any adapter code was written** — `sqlite_vec.load(conn)` (loads the extension into a `sqlite3.Connection`), `sqlite_vec.serialize_float32(vector)` (packs a vector into the wire format `vec0` expects), a `CREATE VIRTUAL TABLE ... USING vec0(embedding float[N] distance_metric=cosine)` schema, `INSERT INTO ...(rowid, embedding) VALUES (?, ?)` (explicit integer rowids, confirmed reusable after a delete, confirmed safe to leave unused since this milestone never deletes), and the KNN query form `SELECT rowid, distance FROM ... WHERE embedding MATCH ? AND k = ? ORDER BY distance` (confirmed: `distance` is `1 - cosine_similarity`; `k` larger than the corpus size safely caps rather than erroring; `k = 0` and an empty table both return `[]` without error; an all-zero, un-normalizable query vector returns `distance = NULL`, not an error or NaN — handled explicitly as similarity 0.0, a degenerate case CLAUDE.md's no-pseudo-embedding invariant means the real embedder never actually produces).
- **A genuine, necessary design adjustment discovered and verified experimentally**: the underlying `sqlite3.Connection` is constructed with `check_same_thread=False`. FastAPI/Starlette's plain-`def` route handlers (every endpoint in this app, including the Phase 1.3 background-task indexing path) run on a shared threadpool, so the same `IndexingEngine`/`VectorIndex` instance can legitimately be called from more than one OS thread across its lifetime — confirmed this is a real characteristic of the existing app, not a new one introduced this milestone. Python's `sqlite3` module refuses cross-thread use of one connection by default (verified: raises `ProgrammingError` without this flag); the pre-Phase-2.2 pure NumPy/list implementation had no such restriction. `check_same_thread=False` was verified experimentally (a real cross-thread write-then-read round trip) to work correctly for this codebase's actual usage pattern. This is disclosed as a necessary adjustment to avoid Phase 2.2 introducing a *new* hard-crash mode, not a claim of full concurrent-write safety — this codebase has no locking around `bm25_index`/`vector_index` today either (unchanged, pre-existing, out of this milestone's scope, matching Phase 2.1's own precedent for `BM25Index`).
- **Architectural decisions made** (all resolved and implemented, none silently inferred):
  1. **Source of truth: SQL remains authoritative; the vector index is a derived, rebuildable search artifact** — unchanged from before Phase 2.2. `hydrate_repository()`/`hydrate_all()` (Phase 0.5, untouched by this milestone) continue to populate the index from durable `EmbeddingModel` rows exactly as before; the sqlite-vec-backed structure itself is an **in-memory-only** (`sqlite3.connect(":memory:", ...)`) SQLite database, confirmed experimentally to hold no on-disk state.
  2. **`.vectors` remains a genuine, correctly-shaped `numpy.ndarray`** (`tests/test_embedding_persistence.py` asserts `.vectors.shape`/`.vectors.shape[1]` directly) — maintained as a parallel, redundant copy of every normalized vector ever added, alongside the sqlite-vec table that actually answers `search()` queries. This is pure bookkeeping for contract compatibility, not a performance-relevant structure, disclosed as such.
  3. **Repository isolation is unchanged**: `VectorIndex` itself has zero awareness of repositories (as before) — the existing `_repo_filter` post-filtering logic in `IndexingEngine.search()` (Phase 0.6, untouched) continues to enforce scoping by reading `metadata["repo_id"]` off each returned candidate, exactly as it always has. `tests/test_repository_scoped_search.py`'s full semantic/hybrid isolation suite (11 tests, including the adversarial overlapping-symbol scenario) passes unmodified.
  4. **No repository-replacement (delete-by-`repo_id`-then-add) idempotency was implemented** — a deliberate scope decision, not an oversight. Unlike Phase 2.1's `BM25Index.remove_repo`, `VectorIndex.add`/`add_batch` remain pure-append operations, exactly matching the pre-Phase-2.2 implementation's own existing behavior. **This is a real, pre-existing gap** (re-indexing an already-indexed repository was already silently accumulating duplicate vector entries before this milestone, since the old `VectorIndex` had no such logic either) that Phase 2.1's analogous fix for `BM25Index` did not extend to here. CLAUDE.md §12 ("do not make opportunistic cleanup... unless required by the current milestone or the roadmap explicitly requires it") governs this: §37 item 2.2's literal text is "adapter... behind existing `VectorIndex` call sites," not an idempotency fix, so this was disclosed rather than silently expanded into. **Explicitly flagged to the user in this session's own final report** as a candidate fast-follow-up, not applied unilaterally. A new test (`test_known_limitation_repeated_add_of_the_same_doc_id_accumulates_duplicates`) documents this exact, current characteristic explicitly, so it cannot silently change (in either direction) without a test noticing.
  5. **Score derivation is unchanged in formula**: `similarity` is recovered as `1 - distance` from sqlite-vec's own cosine distance output, then `relevance_score = clamp((similarity + 1) / 2, 0, 1)` and `embedding_distance = clamp(1 - similarity, 0, 2)` — the exact same formulas the pre-Phase-2.2 NumPy implementation used, only the source of the raw `similarity` number changed (from `np.dot` to a SQL KNN query). `HybridRanker` was **not modified**.
  6. **Vector normalization is unchanged**: both indexed and query vectors are still L2-normalized in Python (via NumPy) before being handed to sqlite-vec, exactly as the pre-Phase-2.2 implementation normalized them before `np.dot` — sqlite-vec's own `distance_metric=cosine` is used as a defense-in-depth match to this, not a replacement for it.
- **Files changed**: `codepulse/search/vector.py` (full rewrite of `VectorIndex`'s internals, same class name/module path/public interface), `pyproject.toml` (new dependency `sqlite-vec>=0.1.9,<0.2.0`, justified by §7's explicit naming), `tests/test_sqlite_vec_semantic_index.py` (new file, 16 tests: 14 unit tests directly against `VectorIndex` — empty index, single/multiple documents, the exact pre-Phase-2.2 `test_vector_index_search` fixture reproduced as a ranking regression proof, similarity/relevance/distance ranges and formulas, metadata and doc_id round-trip, determinism, `top_k` truncation, `.vectors`/`.doc_ids`/`.dimension` attribute contracts, unnormalized-vector handling, all-zero-query safety, empty-batch safety — plus 1 test explicitly documenting the known repeated-add-accumulates-duplicates limitation above, and 1 test proving a genuine vector-layer failure propagates through the existing Phase 1.6 structured 500 envelope rather than a hand-rolled shape). **No line in `codepulse/indexer/engine.py` changed** — unlike Phase 2.1 (which needed one new `remove_repo` call site), Phase 2.2's literal scope required zero call-site changes, since no repository-replacement behavior was added.

- **Architectural decisions made** (all previously flagged by the architecture gate as requiring an explicit choice, now resolved and implemented — none silently inferred):
  1. **Source of truth: SQL remains authoritative; the Tantivy index is a derived, rebuildable search artifact.** No cross-store transactional coordination, no index persistence/versioning/corruption-recovery infrastructure was introduced — matches the pre-existing `BM25Index`'s own characteristic exactly, just re-implemented on Tantivy's engine internally.
  2. **In-memory Tantivy only.** `tantivy.Index(schema)` is constructed with no path argument (confirmed experimentally: genuinely in-RAM, nothing written to disk). No `.codepulse/` directory, no cache-directory configuration, and no on-disk persistence were introduced in this milestone.

  4. **Repository-replacement idempotency: delete-by-`repo_id`-then-add-then-commit.** `IndexingEngine.index_directory()` now calls a new `BM25Index.remove_repo(repo_id)` method once, immediately before the existing per-symbol `add_symbol` loop, deleting every lexical document previously indexed for that repository via `IndexWriter.delete_documents("repo_id", repo_id)` (an exact-term deletion, confirmed safe/no-op when the repository has no existing documents — covering both the first-ever index of a repository and an empty repository). This closes a **real, pre-existing, previously-untested gap**: the old parallel-list `BM25Index` had no doc_id-based replace logic at all, so repeated `index_directory()` calls on an already-indexed repository silently accumulated duplicate lexical documents forever (discovered by direct code inspection during the architecture gate, and confirmed live by the fact that `tests/test_restart_idempotency.py`'s own `test_repeated_reindex_is_idempotent_and_identifiers_stay_stable` — which re-indexes the same repository 5 times into one engine — asserted SQL row-count stability but never checked `bm25_index.num_docs`, so the accumulation had never been caught). Fixing this was judged in-scope because Tantivy's `delete_documents` makes it essentially free and it has zero ranking-contract impact — not because the roadmap's literal Phase 2.1 text mandates fixing pre-existing gaps.
  5. **Tokenization: reuses the existing, already-tested `codepulse.search.tokenizer.tokenize_code`** for both indexing and querying, feeding the resulting space-joined token list into a Tantivy text field configured with the built-in `"whitespace"` tokenizer (not Tantivy's own `"default"` tokenizer, which does not split camelCase identifiers the way `tokenize_code` does). The search corpus construction itself (`name*3 + signature + docstring + extra_text + body[:1000]`) is byte-for-byte unchanged from the pre-Tantivy implementation — no field-specific boosting, no split name/signature/docstring fields, no relevance redesign.
  6. **Score normalization is unchanged in formula**: `normalized_score = raw_score / max(raw_score across this query's result set)`, with the same zero-max safety fallback (`max_score = 1.0` if the true max is `<= 0`) the pre-Tantivy implementation used — reproduced exactly, not reinvented. Tantivy's own BM25 scorer produces genuinely different raw numeric values than the old hand-rolled Okapi BM25 formula (expected and explicitly permitted — the roadmap's "ranking contract" is the *shape/meaning* `HybridRanker` consumes, not bit-identical arithmetic); `normalized_score` remains a float in `[0, 1]`, `HybridRanker` was **not modified**.
  7. **`.k1`/`.b` remain real, settable, readable attributes** (`BM25Index(k1=..., b=...)`, `tests/test_config.py` reads them directly) even though Tantivy's own Python binding exposes no configurable BM25 k1/b parameter anywhere in `Query`/`Searcher`/`Index` (confirmed by full `dir()` introspection — no such method exists). Tantivy's fixed internal BM25 implementation is used as-is; `.k1`/`.b` are preserved purely for interface compatibility, disclosed here rather than silently glossed over.
- **`IndexingEngine.symbols_by_id`/`.symbol_repo_map` staleness is unchanged, not fixed, and not newly introduced by this milestone**: these two dicts (used by the hybrid-search graph-score computation, unrelated to `BM25Index`) already only ever *set* entries for symbols found in the current run, never removing an entry whose symbol no longer exists after a re-index. This pre-existing characteristic is harmless in practice (a stale key never appears in the fresh, repo-replaced Tantivy candidate lists, so it's simply never touched by `fuse()`), was already true before Phase 2.1, and fixing it is out of scope for this milestone (unrelated data structure, not a `BM25Index` call site).
- **Files changed**: `codepulse/search/bm25.py` (full rewrite of `BM25Index`'s internals, same class name/module path/public interface), `codepulse/indexer/engine.py` (one new line, `self.bm25_index.remove_repo(repo_id)`, plus an explanatory comment, immediately before the existing per-symbol lexical-population loop — no other line in this file changed), `pyproject.toml` (one comment updated to note `tantivy` is now actually wired in, no version/dependency-list change), `tests/test_restart_idempotency.py` (one new assertion added to the existing 5-iteration re-index test, proving the previously-undetected lexical-duplication gap above is now closed — no existing assertion removed or weakened), `tests/test_tantivy_lexical_index.py` (new file, 21 tests: 15 unit tests directly against `BM25Index` — empty index, single/multiple documents, the exact pre-Tantivy `test_bm25_search` fixture reproduced as a ranking regression proof, raw/normalized score types and range, metadata and doc_id round-trip, determinism, `top_k` truncation, no-non-matching-results, `.doc_ids`/`.num_docs`/`.k1`/`.b` attribute contracts, `remove_repo` no-op safety — plus 6 integration tests through the real `IndexingEngine` covering exactly Cases A-F of the required repository-replacement behavior, and 1 test proving a genuine lexical-layer failure propagates through the existing Phase 1.6 structured 500 envelope rather than a hand-rolled shape).

### Phase 1.6 — Structured error response format across all endpoints

- **Scope determined from the roadmap's own text** (§37 item 1.6: "Structured error response format across all endpoints"; §21 API Strategy, verbatim: "Errors follow a single shape: `{"error": {"code": "...", "message": "...", "details": {...}}}`"). No dedicated backlog (§45) row exists for this item -- unlike every other Phase 1 milestone, 1.1-1.5 -- so its DoD is defined only by §37's title and §21's literal shape; there is no numeric/behavioral detail beyond that to under- or over-fit.
- **IN scope (implemented)**: a new `codepulse/api/errors.py` module with two global FastAPI exception handlers, registered once (`install_error_handlers(app)`) -- one for `HTTPException` (covers every existing 401/403/404/409/429/501/400 raise site, none of which needed to change), one for `RequestValidationError` (FastAPI's own automatic 422s), plus a catch-all `Exception` handler (500s, logged server-side via `logger.exception`, never leaking the real exception text/traceback to the client). The rate-limit middleware's own 429 (Phase 1.4, previously built as an ad-hoc `{"detail": ...}` dict directly, not raised as an `HTTPException`) was updated to call the exact same shared `error_json_response` helper the exception handlers use, so the envelope-building logic is never duplicated between the two call sites.
- **OUT of scope (explicitly NOT implemented)**: rewriting any error's status code or message wording (this milestone reshapes existing responses, it does not redesign what they say); MCP's own distinct, flatter error shape (roadmap §13: `{"error": "code_string", "message": "..."}`, no "details" -- a different section's requirement for a surface, MCP/Phase 5, that does not exist yet); a security test suite (Phase 1.7).
- **Design decisions made explicitly, not inferred from later milestones**:
  1. **`code` is derived deterministically from the HTTP status via Python's own `http.HTTPStatus` enum** (`HTTPStatus(404).name.lower()` -> `"not_found"`), not an invented per-endpoint string table -- every status code already in use (and any added later) maps correctly without `codepulse/api/errors.py` needing to know about it specifically.
  2. **`details` carries real, already-computed information where it exists, empty `{}` otherwise -- never fabricated.** Currently populated in exactly two cases: the rate limiter's real `retry_after_seconds` (the *same* value already used for the `Retry-After` header since Phase 1.4, not a second independently-computed number) on 429s, and the real Pydantic validation error list on 422s.
  3. **A genuinely unhandled exception (500) never leaks its real message/traceback to the client** -- `message` is the generic, fixed string "Internal server error"; the real exception is logged server-side only (`logger.exception`), matching how this project already treats other server-internal failure information. Verified this really works (not just reasoned about): a deliberately-broken route body was exercised via `TestClient(app, raise_server_exceptions=False)` and confirmed to return a clean structured 500 with no leaked text -- `raise_server_exceptions=True` (Starlette's TestClient default) intentionally re-raises the *original* exception to the calling test code even when an app-level handler already produced a clean response (a testing-visibility feature, not a production behavior), so tests that want to *inspect* the 500 response body must explicitly opt out of that default, which the one test needing it does.
  4. **The rate-limit middleware needed its own explicit fix, not just the global `HTTPException` handler.** Starlette's `ExceptionMiddleware`/`ServerErrorMiddleware` (which dispatch to `@app.exception_handler(...)` registrations) sit *inside* (closer to routing than) a custom `@app.middleware("http")` function in the stack ordering that matters -- an exception raised from *inside* such custom middleware is never seen by those dispatchers, so a plain `raise HTTPException(...)` there would never have reached the new handlers. Both call sites use the same `error_json_response` helper instead, avoiding a second, drifting implementation of the envelope shape.
- **Architecture rule preserved, with a deliberate placement note**: `codepulse/api/errors.py` lives *inside* `codepulse/api/` (unlike `auth.py`/`jobs.py`/`rate_limit.py`/`ingestion_safety.py`, which are top-level modules reusable by a future CLI/MCP surface) -- this is a REST-HTTP-response-shape concern specifically (§21's envelope), not a capability those other surfaces would reuse: MCP has its own, different error shape (§13), and the CLI never returns HTTP responses at all. `IndexingEngine`/`codepulse/indexer/`, `codepulse/storage/db.py`, `codepulse/auth.py`, `codepulse/jobs.py`, and `codepulse/ingestion_safety.py` were not touched.
- **Test impact was small and fully audited before implementing**: a project-wide search found only 2 existing test assertions anywhere that checked the old `{"detail": "..."}` shape directly (`tests/test_ingestion_safety_endpoint.py`, `tests/test_rate_limit_middleware.py`) -- both updated to check the new `error.message`/`error.code`/`error.details` path instead, with no change to what they actually verify. No test anywhere relies on an unhandled exception propagating through `TestClient` (verified via a project-wide `pytest.raises` search before adding the catch-all 500 handler), so that addition carried no regression risk.

### Phase 1.5 — Ingestion safety: path allow-list, SSRF check, size caps

- **Scope determined from the roadmap's own text** (§37 item 1.5; §15 Security Architecture's verbatim "Repository-ingestion safety (the dangerous endpoint)" paragraph: local-path allow-listing + traversal/symlink rejection, git-URL scheme validation + SSRF host check + size/file-count cap "before beginning a full clone"; §15's "Resource limits: max files per repo, max file size parsed..."; backlog B10, DoD "Path traversal / SSRF / oversized-repo attempts rejected with tests proving it"):
  - IN scope (implemented): a new top-level `codepulse/ingestion_safety.py` module -- `validate_local_path` (resolves symlinks/`..`, rejects anything outside a configured allow-list) and `validate_git_url` (scheme + resolved-host SSRF check), both wired into `POST /v1/repositories/index` as synchronous, pre-job checks; a file-count cap and a per-file size cap, both enforced inside `IndexingEngine.index_directory()` (see design decision 5 below for why); three new `CodePulseConfig` fields (`ingestion_allowed_roots`, `ingestion_max_files_per_repo`, `ingestion_max_file_size_bytes`).
  - OUT of scope (explicitly NOT implemented, reserved for later milestones or never assigned to this one at all): actually cloning/fetching a git repository (see design decision 1 below -- this codebase never had that capability, and no sprint item assigns it a milestone); request-body size caps (roadmap §15 lists this as a separate, server/ASGI-layer resource limit, not application code this milestone adds); a global/per-tenant concurrent-job cap (Phase 1.3 already added a *per-repository* advisory lock; §15's "per tenant" wording describes a distinct, unrequested control); a structured `{"error": {...}}` envelope (Phase 1.6); a dedicated security test suite (Phase 1.7).
- **Design decisions made explicitly, not inferred from later milestones**:
  1. **No git-URL fetching was invented.** Grep-confirmed: this codebase has zero git-clone/network-fetch code anywhere (no `subprocess`, `GitPython`, or clone logic). `IndexRepoRequest.source` (`"local"`/`"github"`/`"gitlab"`) has always been accepted but never branched on -- every prior phase silently mis-treated a git URL as a local path, indexing zero files while claiming "queued." Building real git-URL cloning is a much larger, unrequested feature no sprint item assigns a milestone to. What 1.5 *does* own, literally, is the "SSRF check" -- so `validate_git_url` is implemented and tested as a real, standalone safety primitive (ready for whenever a real fetch path exists), and the endpoint now honestly rejects a non-local `source` (after still validating the URL for safety first) with HTTP 501, rather than continuing the silent mis-processing.
  2. **`ingestion_allowed_roots` defaults to `[]` = unrestricted**, the opposite convention from `cors_origins` (which defaults to deny-all). This is deliberate, not an inconsistency: this endpoint acts on behalf of the local user who already has filesystem access to their own machine (CLAUDE.md: "Local mode is the default"), and the roadmap's own promised zero-configuration experience ("`codepulse index .` works with zero external infrastructure") would break if ingestion required allow-list configuration before any use. The interesting case for enforcing a strict allow-list is a server/team deployment exposing this API beyond localhost with a key untrusted parties might hold -- exactly §15's own stated concern, and exactly when an operator would configure the setting.
  3. **Traversal and symlink-escape rejection share one mechanism**: `Path(path).resolve()` (which both collapses `..` segments and follows symlinks) followed by a containment check against the resolved allow-list roots. No separate "reject literal `..` in the string" logic was written, because resolving first and checking containment catches both attack shapes identically and is simpler than pattern-matching the raw string.
  4. **File-count/file-size caps live inside `IndexingEngine.index_directory()`, not at the API boundary as a synchronous pre-flight check.** The file list they check against is only available after the discovery walk `index_directory()` already performs; duplicating that exact walk at the API layer just to pre-count would be wasteful and is exactly the kind of "second identity system"/duplicated-logic this project's established house style avoids (see `codepulse/ingestion_safety.py`'s module docstring). Consequence: a file-count violation surfaces as a **failed job** (poll `GET /v1/jobs/{job_id}`), not a synchronous 4xx like the allow-list/SSRF checks -- a deliberate, documented split between "known before any work starts" (checked synchronously) and "only discoverable once the directory has been walked" (checked as part of the job, surfaced via the existing Phase 1.3 job-failure path). A single oversized file is *skipped* (logged, not fatal), reusing the exact per-file error-tolerance pattern already established for malformed/unparseable files.
  5. **`codepulse/indexer/engine.py` IS modified by this milestone** -- a deliberate departure from Phases 1.2-1.4's "IndexingEngine untouched" pattern, and called out explicitly here rather than silently. File-count/size limits are genuine indexing-pipeline resource-safety concerns (the file list and each file's bytes are only known inside the discovery/parse loop itself), the same category as the engine's own pre-existing "no silent pseudo-embedding fallback" and "embedding model unavailable -> fail explicitly" invariants (§17) -- not an HTTP/auth-coupling violation of CLAUDE.md §3, which is specifically about authentication, not general resource safety. `IndexingEngine` still has zero knowledge of jobs, auth, or rate limiting.
- **Architecture rule preserved otherwise**: `codepulse/ingestion_safety.py` is a new top-level module (not under `codepulse/api/` or `codepulse/indexer/`), mirroring `codepulse/auth.py`/`codepulse/jobs.py`/`codepulse/rate_limit.py`'s placement.

### ⚠️ Incident during migration verification (Phase 1.3, found and fully remediated in that session -- kept here verbatim as accurate project history, not touched by Phase 1.4 or 1.5)

While running an ad-hoc Python one-liner to sanity-check new routes (`import codepulse.api.app as app_module; ...`), that import's module-level `storage_manager = StorageManager()` executed against the **default** `db_url` (`sqlite:///codepulse.db`, the real database) because the command was run without a `CODEPULSE_DB_URL` override. `StorageManager.__init__` unconditionally calls `Base.metadata.create_all(bind=self.engine)` **alongside** Alembic -- an already-documented, pre-existing piece of technical debt -- which silently created the new `index_jobs` table directly on the real `codepulse.db`, bypassing Alembic entirely and leaving `alembic_version` stale.

**Caught immediately** when applying the real Phase 1.3 migration to a disposable copy of `codepulse.db` failed with `table index_jobs already exists`. **Verified before remediating**: the accidentally-created table's schema was byte-for-byte identical to the migration's own definition (expected, since `create_all()` uses the exact same SQLAlchemy model), empty, and no pre-existing data was touched. **Remediated** via `stamp_database(revision="de22df2fc3ce")` -- Alembic's own non-destructive mechanism for tracking an already-correct schema -- applied to the disposable copy first, then identically to the real database. **No data was lost.**

**Lesson re-applied in both Phase 1.4 and Phase 1.5**: `codepulse.api.app` was again imported ad-hoc for sanity checks in both sessions, without an isolated DB URL. In neither case did this matter, because neither milestone added a new model to `codepulse/storage/db.py` -- `create_all()` had nothing new to create either time -- and the real `codepulse.db` was explicitly re-verified unchanged (schema and every row count) immediately afterward in both sessions.
