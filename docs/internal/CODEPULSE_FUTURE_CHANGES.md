## 1. Search relevance scores are per-chunk, not per-symbol

**Found**: 2026-09-26, while manually testing `search` via the QA checklist (CLI-q-1 vs. CLI-q-2).

**The problem**: `codepulse/search/ranker.py`'s `fuse()` computes `relevance_score` per candidate `doc_id` — and a single symbol is split into multiple chunks (signature, docstring, body) at index time. BM25 (keyword) and the vector index each independently pick their own best-matching chunk for a symbol, and those are frequently *different* chunk rows. The fusion formula (`0.40×KW + 0.40×Vec + 0.20×Graph`) then never gets to combine a high keyword score and a high vector score into one number for that symbol, because no single row has both.

**Concretely observed**: querying `"distance between points"` against `Test_Repo` surfaced `calculate_distance` three times — `KW=1.00/Vec=0.00` (→ `0.44`), `KW=0.00/Vec=0.84` (→ `0.34`), `KW=0.00/Vec=0.83` (→ `0.33`) — three separate rows, each scored on only one axis, instead of one row reflecting that the symbol actually matched on *both*. Compared against a genuinely irrelevant query (`"xyzzy quantum toaster nonsense"`, top hit `0.24`, pure vector noise with `KW=0.00, Graph=0.00`), the gap between "this is a great match" (0.44) and "this is noise" (0.24) reads far smaller than it should, because the good match's true combined signal was never actually computed as one score.

**Verified formula** (`ranker.py`'s `fuse()`): `combined = weight_keyword×KW + weight_vector×Vec + weight_graph×Graph` (+ an exact-name-match boost when the query literally names the symbol), defaults `0.40 / 0.40 / 0.20`. Confirmed by hand-computing both cases above against the real weights and getting exact matches.

**Not a bug** — chunking finely for embeddings is a reasonable, deliberate design choice. But it means a general user reading the CLI/VS Code's `relevance_score` column has no way to tell "this scored low because it's genuinely irrelevant" apart from "this scored low because its keyword-match and semantic-match landed on different chunks" — both look like an unremarkable ~0.2–0.4 number.

### Options considered (none implemented yet)

1. **Symbol-level result aggregation (recommended starting point)** — group chunk-level candidates by `(symbol_name, file_path)` *after* fusion, take the max KW/Vec/Graph across a symbol's own chunks, recompute one combined score from those maxes. `calculate_distance` would show as one row at `~0.74` instead of three rows at `0.44/0.34/0.33`. Should live at the **display layer** (CLI output formatting, VS Code's search quick-pick) — not inside `IndexingEngine.search()`/`ranker.fuse()` itself, since MCP tool callers (agents) may genuinely want the finer per-chunk granularity `search_code` currently returns. Needs a decision on which chunk's snippet represents the merged row, and real verification against `tests/relevance/dataset.json` that this doesn't distort anything currently depended on.
2. **Pure presentation fix, no scoring change** — collapse same-symbol rows in the CLI/VS Code UI without changing the underlying numbers; show "3 matching chunks — keyword ✓, semantic ✓" instead of 3 separate scores. Lower risk than #1 (touches only rendering, not `ranker.py`), but doesn't fix the actual "0.44 looks weak" perception problem, just makes the multi-chunk pattern visible.
3. **Align BM25 and vector chunk boundaries** — the deeper fix, so keyword and semantic search are more likely to land on the *same* chunk in the first place. Real risk to indexing internals; would need `tests/relevance/dataset.json` re-validation before trusting it, and is a bigger unit of work than #1/#2.

**Recommendation when this gets picked up**: start with #1, scoped to the CLI/VS Code display layer only, `search()`'s own return contract to MCP/REST callers left untouched.

## 2. Repository path matching doesn't normalize backslash vs. forward-slash — **RESOLVED 2026-10-14** (see CODEPULSE_PROGRESS.md, "One repository, one identity")

> **Update 2026-10-12 (found by the real-VS-Code tests): this now has a user-visible effect.** VS Code reports a Windows folder as `c:\\...` (lowercase drive) while a repository indexed from the CLI is stored as `C:\\...`. The extension matches case-insensitively when it looks a folder up, but sent the raw path to `POST /v1/repositories/index`, which compares the URL string exactly, so clicking Index Workspace created a DUPLICATE repository (a new id) that the user's key could not see, instead of re-indexing the existing one. The extension now sends the stored URL when the folder matches (commit in `codepulse-vscode`), which removes the symptom for re-indexing, but the server still treats `c:\\x` and `C:\\x` as different repositories for every other client (CLI, MCP, REST). Canonicalizing repository identity on the server (case on Windows, slashes, trailing separators), with a migration for existing URLs, remains the real fix.

**Found**: 2026-09-26, while building the QA checklist's REST API test cases (rest-6).

Already flagged as its own tracked follow-up task (`task_de0daaea`, spawned mid-session) rather than duplicated in full here — see that task's own description for the full repro and fix sketch. Summary: `POST /v1/repositories/index`'s "is this repository already known" check (`RepositoryModel.url == req.url`, in `codepulse/api/app.py`) is a plain string comparison, so indexing the same directory with backslashes vs. forward slashes creates two separate repository rows instead of recognizing them as the same repo — and, as a side effect, lets a viewer-role key bypass the "re-indexing an existing repo requires indexer role" check, since the differently-spelled path looks like a brand-new repository to that check.

## Items 3-9: found by the 2026-10-02 resumption audit

Full evidence, root causes and verification are in `CODEPULSE_PROGRESS.md` ("Audit 2026-10-02"). Each was reproduced live. Items 3-6 were fixed on 2026-10-12; 7-9 and 10-12 are open. Listed in suggested priority order, not finding-letter order.

### 3. No `codepulse` executable (audit finding E) — Medium — **RESOLVED 2026-10-12**
`pyproject.toml` has no `[project.scripts]`, so only `python -m codepulse.cli` works. The VS Code extension's default `codepulse.serverCommand` is `codepulse`, which therefore fails out of the box (the manual had to tell users to change it). **Fix sketch**: add `[project.scripts] codepulse = "codepulse.cli:main"`, `pip install -e .`, verify `codepulse --help` and the extension's default launch. Smallest change with the largest "works first time" payoff.

### 4. Nonexistent local paths are accepted and create phantom repositories (finding A) — Medium — **RESOLVED 2026-10-12**
`python -m codepulse.cli callers /no/such/path foo` exits 0 with "0 found", and `POST /v1/repositories/index` with a bogus path returns `202` and a job that "succeeds" with 0 files — both leave an empty repository row. The real `codepulse.db` contained one from the manual's literal placeholder command (removed 2026-10-02 at the user's instruction; the bug itself is still open). **Fix sketch**: in `ingestion_safety.validate_local_path` (and the CLI's path handling) require `Path(...).is_dir()`; REST → `400` with a clear message, CLI → error + non-zero exit. Add tests for both. Interacts with item 2 (path normalization): do them together.

### 5. README is inaccurate and has no usage section (finding B) — Medium (docs) — **RESOLVED 2026-10-12** (README rewritten; a `codepulse keys create` command is still a possible follow-up)
Claims `pgvector`, Redis Streams and Docker prerequisites; none exist (actual stack: SQLite + sqlite-vec + Tantivy, in-process, no Docker). No instructions for the CLI, `serve`, or bootstrapping the first API key (which currently requires a Python snippet because the REST key endpoint needs an existing admin key). **Fix sketch**: rewrite to the real architecture; add a short "first run" section; consider a `codepulse keys create` CLI command so bootstrapping isn't a Python one-liner.

### 6. Routing-level 404/405 skip the structured error envelope (finding F) — Low — **RESOLVED 2026-10-12**
Unknown route → `{"detail":"Not Found"}`, wrong method → `{"detail":"Method Not Allowed"}`, while every application-raised error uses the §21 `{"error":{...}}` envelope. Cause: `api/errors.py:129` registers its handler on `fastapi.HTTPException`, but Starlette's router raises the base `starlette.exceptions.HTTPException` (fastapi's is a subclass, so the handler never matches). **Fix sketch**: register the handler on `starlette.exceptions.HTTPException`; add a test for an unmatched route and a wrong method.

### 7. Default rate limit vs. the VS Code extension (finding D) — Low-Medium
5 req/s sustained, burst 20, per API key. Measured with the extension's real compiled client: 12 cursor settles in 5.5 s (48 requests) → 3 got `429` (6%); the extension has no retry, and `listRepositories()` (uncached) is ~25% of its traffic. **Fix sketch** (extension repo): cache the workspace→repository resolution for ~30 s and retry once on `429` honoring `retry_after_seconds`. Optionally revisit the server default for loopback/local-first use (it is already tunable via `CODEPULSE_RATE_LIMIT_*`).

### 8. Fresh databases are never Alembic-stamped (finding C) — Low-Medium, latent — **RESOLVED 2026-10-14** (see CODEPULSE_PROGRESS.md, "codepulse migrate")
Any DB created by the first CLI/`serve` run goes through `create_all()` with no `alembic_version` table, and nothing stamps it; `migrations.stamp_database()` exists but is never called, and the CLI has no migrate/stamp command. Harmless until the next schema migration ships — then every user DB needs a manual stamp first. **Fix sketch**: stamp `head` right after `create_all()` on a brand-new DB, and/or add `codepulse migrate`.

### 9. SSRF check rejects NAT64 addresses (finding G) — Low, latent
`validate_git_url` treats `64:ff9b::/96` (DNS64-synthesized) as reserved, so on an IPv6-only/DNS64 network every public git host (github.com → `64:ff9b::14cf:4952`) is refused as an SSRF risk. No current impact (git ingestion returns 501 anyway). **Fix sketch** when git cloning is implemented: extract the embedded IPv4 from NAT64 addresses and validate that instead.

### 10. Built wheel is missing `alembic.ini` and the migrations (finding K) — Medium (packaging) — **RESOLVED 2026-10-14** (see CODEPULSE_PROGRESS.md, "codepulse migrate")
`migrations.get_alembic_config` resolves `alembic.ini` and `alembic/` relative to the source tree, so a non-editable `pip install` (or a built wheel) ships without them and any migration call fails. Editable installs work, which is why this was never hit. **Fix sketch**: ship the migrations inside the package (or `package-data`) and resolve them via `importlib.resources`. Pairs naturally with item 8 (stamping/migrating fresh databases).

### 11. Lint and type checks are declared but never run (finding L) — Low (hygiene)
`ruff` and `mypy` are dev dependencies, yet neither runs in CI. Current counts: ruff 124, mypy 118, mostly noise (FastAPI `Depends()` default args, SQLAlchemy typing). Real minors: ~16 unused imports, ~16 blind `except Exception`, 7 `datetime.utcnow()` uses; five subpackages have no `__init__.py`. **Fix sketch**: configure ruff to ignore the framework noise, fix the real minors, then add ruff to CI. Do it as one dedicated cleanup milestone, not opportunistically.

### 12. `api_errors_total` is labelled by raw path for matched routes (finding N) — Low
Fix F collapsed unmatched paths into `endpoint="unmatched"`, but matched routes still use `request.url.path`, so `/v1/symbols/{id}` creates one Prometheus series per id. **Fix sketch**: label by the route template (`request.scope["route"].path`) in `_record_api_error`, and update `test_a_404_response_increments_api_errors_total`, which currently asserts the concrete path.

### 13. The call graph is not restored after a server restart, so callers/impact silently read 0 (found by the real-VS-Code QA run) — High (correctness) — **RESOLVED 2026-10-12** (call graph in `97f81d8`; symbol map in the commit that follows it). See the "Restart restore" entry in CODEPULSE_PROGRESS.md.
`IndexingEngine.hydrate_all()` restores embeddings and the keyword index at startup, but not `call_graphs`. After any restart, `POST /v1/symbols/{id}/impact-analysis` and the references endpoint return empty results (`direct_callers: 0`) with no indication the graph is cold, so the VS Code CodeLens shows "0 callers" and the References sidebar "Subclasses (0)" for symbols that do have them. Reproduced over REST (`add`: 0 after restart, 4 after a re-index) and in a real VS Code window. The extension's normal flow (it launches `codepulse serve`, or the user restarts it) hits this every time. The data needed is durable: the `call_edges` table (with confidence) exists. **Options**: (a) rebuild each repository's call graph from `call_edges` at startup (real fix; must keep results identical to a fresh index, including confidence); (b) answer from `call_edges` directly when the in-memory graph is cold; (c) at minimum make the cold state explicit in responses (a `graph_status: cold` field) and have clients show "re-index to enable call graph" instead of 0. Violates the spirit of "call-graph uncertainty represented" and "explicit omission" until fixed. Earlier notes in this file call the limitation "known"; this item records that it is user-visible.

### 14. Extension traffic profile (data for item 7)
In the real-window run, `GET /v1/repositories` was 26 of 73 requests (36%) and `POST .../impact-analysis` 30; no 429 occurred. Caching the workspace-to-repository resolution would remove about a third of the traffic.

### 15. Module structure is empty after a server restart (found while verifying item 13) — Medium — **RESOLVED 2026-10-12** (commit `0a01b0b`, option (a): persisted import edges)
`GET /v1/repositories/{id}/modules` and the VS Code Module Structure command return 0 clusters on a freshly restarted server and 6 after a re-index (Test_Repo). The module graph is built from each file's parsed imports (`IndexingEngine.parse_results`), and imports are not persisted anywhere, so unlike the call graph (`call_edges`) and the symbol map (`symbols`/`files`) it cannot be rebuilt from the database. **Options**: (a) persist per-file import edges at index time (a new table + Alembic migration) and rebuild the graph from them at startup; (b) re-parse the repository's files from disk on first use when the cache is cold (no schema change, but reads disk state that may differ from the indexed snapshot, so results could drift from the index); (c) at minimum return an explicit `graph_status: cold` instead of an empty-but-valid-looking result. Same class of problem as item 13 (a confident empty answer after a restart), smaller blast radius: only this one view is affected.

### 16. A full re-index never deletes the database rows of files that no longer exist (found while verifying item 15) — Medium (correctness) — **RESOLVED 2026-10-12** (commit `1b00cae`)
`_persist_to_db` upserts the current files but never removes `files`/`symbols`/`code_embeddings` rows for files that have since been deleted or ignored; only the INCREMENTAL path purges them (`_purge_stale_entries`). A full run is forced for non-git repositories, for a first run, and after every server restart, so in practice deleted files linger. Reproduced: index two files, delete one, re-index (full), restart, and the deleted file's symbol is back in keyword search and in the restored symbol map (keyword search always did this; restoring the symbol map made it visible in autocomplete and graph scoring too). The persisted module graph and call graph are NOT affected (they are rewritten from the current parse set), which is why the module-edge rows store the node set explicitly. **Fix sketch**: at the end of a full run, call `_purge_stale_entries(repo_id, stale_relpaths)` for the repository's stored paths that are not in this run's parsed set (it already handles the database rows, BM25, the vector index, the symbol maps and the parse cache). Needs its own test for ignore-rule and size-cap cases (a file that becomes ignored should also leave the index) and a decision on the rare case of a transiently unreadable file being purged until the next successful run.

### 17. No command to migrate or stamp a database (extends item 8) — Low-Medium — **RESOLVED 2026-10-14** (see CODEPULSE_PROGRESS.md, "codepulse migrate")
Adding the `module_edges` migration made this concrete: an Alembic-managed database (the real `codepulse.db`) needs `alembic upgrade head` run by hand from the repository root, there is no `codepulse migrate`, and a database CodePulse created itself is never stamped, so it silently gets new tables through `create_all` but cannot be upgraded the Alembic way later. The new code degrades safely on an unmigrated database (one logged warning, module structure not restart-proof), so nothing breaks, but a user has to know to migrate. **Fix sketch**: `codepulse migrate` (upgrade head, stamping an unstamped database first), run automatically or offered by `serve`/`doctor` when the revision is behind.

### 18. Indexing a never-indexed folder from the extension cannot complete with a scoped key (found by the real-VS-Code tests) — Medium — **RESOLVED 2026-10-14** (option (a), user-approved; see CODEPULSE_PROGRESS.md)
`POST /v1/repositories/index` lets any valid key create a NEW repository (the grant check only runs when the repository already exists), but `GET /v1/jobs/{id}` requires a grant on the job's repository, which the creating key does not have. So VS Code's Index Workspace on a new folder ends with "lost track of indexing job job_N: API key is not scoped to repository M", the job still runs, the repository exists, and the key can never see it (the folder keeps reading "not indexed"). Reproduced in a real window (suite check `E3`, reported as a known gap). **Options**: (a) when a key creates a new repository, give that key an `admin` grant on it (owner semantics), and restrict creation to keys that already hold `indexer` or higher on some repository (today even a viewer-only key can create repositories); (b) a separate admin-only repository-creation endpoint, with Index Workspace explaining that a key scoped to the new repository is needed; (c) at minimum, a clear extension message instead of "lost track". (a) makes the extension flow work and is a small change, but it is an RBAC decision (Phase 7.2), so it needs an explicit go-ahead.

## Items 18-30: found by the 2026-10-15 publication audit (measured on an idle machine; see CODEPULSE_PROGRESS.md)

### 19. Indexing silently lost data on any real-sized repository (P0) — **FIXED 2026-10-15**
Two defects. A regression from the module-edges work: `_module_edges_table_exists` inspected the database through a SEPARATE connection while the save transaction was open; once that transaction outgrew SQLite's page cache it was refused ("database is locked") and the whole save failed. And an older flaw that hid it: `_persist_to_db` swallowed every exception and `index_directory` carried on, recorded a snapshot and reported success. A 46-file index left a repository row with 0 files, symbols and embeddings. Every test indexed a tiny repository, and the relevance test only queries in-memory indexes, so nothing noticed. Fixed: the check uses the session's own connection; a failed save raises `IndexingPersistenceError`, records no snapshot, and the in-memory indexes are restored from the database; REST reports a failed job with the real message and the CLI a clean error. Tests: `tests/test_index_persistence_integrity.py` (6).

### 20. Hybrid search does not beat its parts on realistic queries; half the top-10 is repeats — High (product claim)
Measured on the 141-query self-benchmark. Of those, 100 are docstring-derived (the query IS the docstring text, so keyword search scores Recall@10 1.000 and the set says little) and 41 are hand-written paraphrases (the realistic test). On the paraphrases: keyword 0.732 / semantic 0.732 / **hybrid 0.659** / rrf 0.780 Recall@10 (MRR 0.458 / 0.568 / 0.476 / 0.423). About **46% of the top 10 in semantic and hybrid modes are repeats of a symbol already shown** (several chunks of one function); keyword has none. Collapsing repeats to one row per symbol lifts semantic paraphrase Recall@10 to 0.878 (MRR 0.598) and hybrid to 0.732, so per-symbol aggregation (item 1) is the biggest single win, and the 0.4/0.4/0.2 fusion still trails semantic-only on paraphrases and needs tuning against the benchmark (weight tuning is not learned ranking). The regression gate (Recall@10 >= 0.85, MRR >= 0.65) is met largely thanks to the docstring-derived queries; report both subsets, and grow the paraphrase set (41 is a small sample, so differences of a few points are noise).
**Status 2026-10-17: PART 1 FIXED (root cause), PART 2 OPEN.** The duplicates were a symptom. The lexical index holds one document per SYMBOL (`repo::file::symbol`) and the vector index one per CHUNK (`repo::file::symbol::chunk_index`, about 2.5 per symbol); fusion merges by `doc_id`, so a symbol's keyword score and its chunk's vector score never met ("hybrid" was two disjoint lists interleaved; RRF never added a symbol's two ranks), and semantic-only rows had no type/signature/docstring/language because chunk metadata has none. Fixed in `IndexingEngine._fold_vector_hits_by_symbol`, used by the semantic, hybrid and rrf modes of `search()` and by `find_similar_symbols` (which listed one symbol up to 9 times): one row per symbol, the best chunk's score (ties by chunk id), symbol-level metadata, ordered best score then id; the unscoped vector pool grew to `limit*6` chunks so folding still fills `limit`. Tests: `tests/test_search_symbol_aggregation.py` (14; 10 were red first). Measured on ONE index, same 141 queries, old behaviour vs new (Recall@10 / MRR): semantic 0.837/0.622 -> 0.950/0.681; hybrid 0.872/0.683 -> 0.929/0.810; rrf 0.936/0.640 -> 0.957/0.785; keyword unchanged 0.915/0.815 (it is the control). Hand-written paraphrases only (41): semantic 0.732/0.574 -> 0.878/0.604; hybrid 0.659/0.477 -> 0.756/0.520; rrf 0.780/0.418 -> 0.854/0.588; keyword 0.707/0.457 unchanged. Repeats in the top 10: about 46% -> 0.0%. (Keyword's absolute numbers differ slightly from the 2026-10-15 audit run because the indexed package itself has changed since; the old/new comparison above is on a single index.) STILL OPEN (part 2): on the realistic paraphrases hybrid (0.756) still trails semantic alone (0.878), so the 0.4/0.4/0.2 weights are not paying for themselves there. One cause worth checking is scale: BM25 scores are normalised to 0..1 while the vector score is `(cosine+1)/2`, which lives in roughly 0.5..0.9, so the vector term dominates or flattens. Re-tuning weights or rescaling is a ranking change that the roadmap wants kept to configurable defaults and judged on the relevance harness; with 41 paraphrases (one query is 2.4 points) it risks fitting our own benchmark, so grow the paraphrase set first. Not done; needs a decision.

**Status 2026-10-18: PART 2 DONE (the scale mismatch), with a documented trade-off.** The lexical score handed to fusion is RELATIVE (`score / best score`, so the top keyword hit is always 1.0), while the semantic score was `(cosine + 1) / 2`, an absolute number in roughly 0.5..0.9 for real code. They were weighted 0.4 / 0.4 as if on one scale, so a weak keyword match counted as much as a strong semantic one. Now the fusion input is `(sim - floor) / (top - floor)` clipped to 0..1, `top` = the best similarity for the query, `floor` = the similarity of the hit at rank `vector_floor_rank` (new setting, default 20, env `CODEPULSE_VECTOR_FLOOR_RANK`, `[search] vector_floor_rank`; 0 restores the old scaling). It depends only on the top 20 hits, so a result scores the same whatever `limit` was asked for (a whole-list min-max looked slightly better on the tuning data but made scores depend on the pool size, so it was rejected). The reported `vector_score` stays the real value. The roadmap's default weights (0.4 / 0.4 / 0.2) are UNCHANGED. Also changed: semantic-only search (`search_type=semantic`) no longer goes through the weighted fuser; `HybridRanker.rank_by_similarity` ranks purely by similarity with no exact-name boost and reports the real relevance as its score. The old path scored `0.4 x relevance + 0.15 boost` (a narrow 0.2-0.36 band), in which a symbol whose name merely appeared inside the query text jumped past much closer matches: starlette MRR 0.272 against 0.551 without the boost. The scores semantic results report are therefore higher than before (the raw relevance, not 0.4x). Method (to limit overfitting): two NEW query sets over installed third-party packages, written from reading each symbol's code before any search result was seen, validated against the parsed symbol tables: `tests/relevance/external_starlette.json` (43, TUNING) and `tests/relevance/external_pathspec.json` (31, HELD-OUT: not loaded while the setting was chosen). Chosen on CodePulse's 41 paraphrases + starlette only (84 queries); the 100 docstring queries were a no-regression guard; pathspec was then evaluated through the real product path. The decision rule (keep roadmap weights, fix only the scale) was fixed before the held-out run. Results through `engine.search`, real model, Recall@10 / MRR, ORIGINAL hybrid -> NEW hybrid: CodePulse paraphrases (41) 0.659/0.477 -> 0.854/0.643; CodePulse docstring queries (100) 0.960/0.767 -> 1.000/0.968; starlette (43) 0.442/0.241 -> 0.837/0.548; pathspec HELD-OUT (31) 0.677/0.398 -> 0.903/0.719. What it does NOT give: hybrid still finds the right symbol in the top 10 slightly LESS often than semantic alone on two of the three paraphrase sets (CodePulse 0.854 vs 0.951; starlette 0.837 vs 0.884; pathspec 0.903 vs 0.839) while ranking it higher (MRR 0.643 vs 0.615; 0.548 vs 0.544; 0.719 vs 0.505). Option C (weights .3 / .7 / 0, no graph term) raises recall (0.927 / 0.884 / 0.935) but lowers MRR on starlette and pathspec (0.562, 0.592), so it was NOT made the default; it is available through config. The graph term (caller count) is a popularity prior unrelated to the query and looked unhelpful on the tuning data; left at the roadmap weight pending a decision. Not changed, but measured: RRF with the conventional k=60 trails k=10 on starlette (MRR 0.478 vs 0.522), so the `rrf_k` default may deserve a look; the exact-match boost in hybrid and keyword modes makes no measurable difference (within noise). Caveats: 43 + 31 external and 41 CodePulse paraphrases are small samples (one query is 1.4-2.4 points), the three codebases are all Python, and the queries were written by the same person who chose the settings. Permanent guards: `tests/test_relevance_external.py` (starlette + pathspec floors, plus 'pooled over both codebases, hybrid MRR beats semantic-only and keyword-only and hybrid recall is not below keyword'), a paraphrase-only gate in `tests/test_relevance_eval.py`, and the main gate ratcheted from Recall@10 0.85 / MRR 0.65 to 0.92 / 0.80 (measured 0.957 / 0.874). `tests/test_vector_score_scaling.py` pins the scaling rules (16 tests).

### 21. First full index is slow: about 13-15 embeddings per second on CPU — Medium (performance)
46 files / 357 symbols / 1,210 chunks took 75 s; 110 files / 1,380 symbols took 125-184 s. Raw encode throughput is 12.6 chunks/s regardless of batch size (torch 2.3.1+cpu, 14 threads): chunks average 1,343 characters (~350 tokens, truncated by the model at 256). A 1,000-file repository would take on the order of half an hour. Incremental updates are fast (one changed file: 0.55-1.5 s, 120-225x faster). Ideas: embed only what the model can use (cap chunk length), skip low-value chunk types, an ONNX/quantized model, or index lexically first and embed in the background.

### 22. Dependency pins are far behind and carry known advisories — Medium (hygiene)
`pip-audit` on the exact installed versions: 39 distinct advisories in 6 packages (starlette 0.37.2: 7; torch 2.3.1: 20; transformers 4.57.6: 6; mcp 1.10.1: 3; pyjwt: 2; sentence-transformers 3.0.1: 1).
